# Hand-off note: dedicated "offline refresh" grant type at the token endpoint

## Goal
Add a new, separately named grant type at the token endpoint that refreshes an access token **only** for offline (long-lived, non-interactive) refresh tokens. Presenting an ordinary (online) refresh token must fail with `invalid_grant` **before** any token is issued, as a normal protocol error response (not a 500). The new grant must show up in `grant_types_supported` in the OIDC discovery document.

## What to imitate
Grants are a pluggable SPI:
- `server-spi-private/.../protocol/oidc/grants/OAuth2GrantType.java` — provider interface (`process(Context)`, `getEventType()`, `getTokenParameterNames()`, optional `preProcess`, `isTokenAllowed`), plus the `Context` holder built by the endpoint.
- `.../grants/OAuth2GrantTypeFactory.java` — factory; `getId()` is the `grant_type` value, `getShortcut()` is the short identifier stamped into tokens and is documented as *unique across grants*.
- `.../grants/OAuth2GrantTypeSpi.java` — SPI name `oauth2-grant-type`, internal.

Closest model to copy: `services/.../grants/RefreshTokenGrantType.java` and `RefreshTokenGrantTypeFactory.java` (id = `OAuth2Constants.REFRESH_TOKEN`, `GRANT_SHORTCUT = "rt"`). The existing refresh flow reads the `refresh_token` form param, fires `TokenRefreshContext` client policies, verifies the token via `tokenManager.verifyRefreshToken`, then delegates to a `RefreshTokenProvider` chosen from the provider factories stream, and reports errors with `CorsErrorResponseException` + `event.error(...)`. Both classes extend `OAuth2GrantTypeBase`. Sibling grants (client credentials, token exchange, CIBA, pre-authorized code, JWT authorization) are in the same package and show the same factory/impl pairing.

Offline-vs-online detection: `core/.../util/TokenUtil.java` has `isOfflineToken(String refreshToken)` / `TOKEN_TYPE_OFFLINE` (also `isOfflineTokenRequested`).

## Dependencies between changes
1. New grant-type constant (likely in `core/.../OAuth2Constants.java`, where all other grant URNs live).
2. New grant impl + factory in `services/.../protocol/oidc/grants/`, registered as a `OAuth2GrantTypeFactory` service.
3. Unique-shortcut enforcement: the uniqueness rule is only stated as a Javadoc contract on `getShortcut()`; the record does not show where (or whether) it is enforced, so a startup-time check that fails hard on duplicates likely has to be added.
4. Discovery: `services/.../OIDCWellKnownProvider.getGrantTypesSupported()` builds the list from the `OAuth2GrantType` provider factories stream, so a correctly registered factory should appear automatically — verify rather than hard-code.

## Easy to miss
- `TokenEndpoint.processGrantRequest` (`services/.../endpoints/TokenEndpoint.java`, ~321 lines) resolves the grant in `checkGrantType()` and special-cases some grant types (UMA, pre-authorized code) to skip `checkClient()`/duplicate-param checks — check whether your grant needs any such handling; also `checkParameters()` and DPoP handling run for every grant.
- Reject the wrong token type before minting: do the offline check ahead of the refresh delegation.
