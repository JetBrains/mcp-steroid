Hand-off note: dedicated non-interactive token renewal grant

Repository: Keycloak. All OAuth2 grant types are pluggable providers behind an internal SPI.

What to imitate
- SPI contract lives in `server-spi-private/src/main/java/org/keycloak/protocol/oidc/grants/`: `OAuth2GrantTypeSpi` (SPI name `oauth2-grant-type`, internal), `OAuth2GrantType`, `OAuth2GrantTypeFactory`.
- `OAuth2GrantType` (a `Provider`) declares: `getEventType()`, `getTokenParameterNames()`, `Response process(Context)`, plus defaults `getSupportedMultivaluedRequestParameters()`, `preProcess(session, formParams)` and `isTokenAllowed(session, token)`. `Context` carries session, realm, client, clientConfig, clientAuthAttributes, request/response/headers, formParams, event, cors, tokenManager, grantType, protocol.
- `OAuth2GrantTypeFactory` adds `String getShortcut()`, documented as a ~3-letter identifier stamped into issued tokens and required to be **unique across grants** — this is the invariant the task mentions.
- Closest model for the new grant: `services/src/main/java/org/keycloak/protocol/oidc/grants/RefreshTokenGrantType.java` and `RefreshTokenGrantTypeFactory.java`. There is also a shared base class `OAuth2GrantTypeBase.java` in the same package that most grants likely build on (contents not inspected).

What has to change, and the dependency order
1. Add the new grant type + factory in `services/src/main/java/org/keycloak/protocol/oidc/grants/`, delegating to the existing refresh-token behaviour after a check that the presented token is a long-lived/offline credential; reject an ordinary session token with an OAuth `invalid_grant` error response (a protocol error, not a 500) **before** any token is issued.
2. Register the new factory in `services/src/main/resources/META-INF/services/org.keycloak.protocol.oidc.grants.OAuth2GrantTypeFactory` — currently ten entries, one line per factory class. Without this line the grant will not be discovered.
3. Give the factory a shortcut not used by any existing factory; if shortcut uniqueness is not already enforced at startup, add that validation so a duplicate prevents boot.
4. Advertise the grant in the well-known/OIDC configuration metadata (`grant_types_supported`); the exact class was not identified in this record.

Easy to miss
- `services/target/classes/META-INF/services/...` is build output; edit only the `src/main/resources` copy.
- The token endpoint dispatcher is `services/src/main/java/org/keycloak/protocol/oidc/endpoints/TokenEndpoint.java`; check whether it maintains its own list of accepted grant-type names, and whether the grant name constant belongs in `OAuth2Constants`.
- Pick a distinct `EventType` so the new operation audits separately.

Verification
- Existing grant tests live under `services/src/test/java/org/keycloak/protocol/oidc/grants/` (e.g. `PreAuthorizedCodeGrantTypeTest`); mirror that for the new grant, covering success with a long-lived credential, `invalid_grant` for a session credential, metadata advertisement, and startup failure on duplicate shortcut.
