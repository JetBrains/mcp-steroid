## Hand-off: dedicated offline/refresh grant at the token endpoint

**What to imitate**
- SPI: `OAuth2GrantType` + `OAuth2GrantTypeFactory` in `server-spi-private/.../protocol/oidc/grants/`. A grant provides `process(Context)`, `getEventType()`, `getTokenParameterNames()`, `preProcess`, `isTokenAllowed`; the factory provides `getId()` (the wire `grant_type` value) and `getShortcut()`.
- Closest behavioural template: `services/.../protocol/oidc/grants/RefreshTokenGrantType.java` — reads `refresh_token`, triggers client policies, calls `tokenManager.verifyRefreshToken(...)`, then delegates to the highest-order `RefreshTokenProvider` (`services/.../protocol/oidc/refresh/`) and builds the response. Extending/mirroring it is the natural route.
- Closest structural template: `JWTAuthorizationGrantTypeFactory` (newest grant): id from an `OAuth2Constants` field, a short `getShortcut()` (`"ag"`), `create()`, and optional `EnvironmentDependentProviderFactory`/`Profile` feature gating. The commit that added it ("Experimental feature for JWT Authorization Grant") touched: `Profile`, `OAuth2Constants`, grant + factory, the services registration file, a test, plus a request class and method in the test OAuth client.

**Change order / dependencies**
1. New grant-type id constant in `core/.../OAuth2Constants.java`.
2. New grant class + factory in `services/.../protocol/oidc/grants/`, with a unique shortcut (other factories expose it as a `GRANT_SHORTCUT` constant).
3. Register the factory in `services/src/main/resources/META-INF/services/org.keycloak.protocol.oidc.grants.OAuth2GrantTypeFactory`.

**Easy to miss**
- Metadata is automatic: `OIDCWellKnownProvider.getGrantTypesSupported()` derives `grant_types_supported` from all `OAuth2GrantType` factory ids; likewise `TokenEndpoint.checkGrantType()` resolves the grant by id, so no dispatch code is needed.
- Shortcut uniqueness is enforced at startup in `DefaultTokenContextEncoderProviderFactory.postInit` (duplicate ⇒ `IllegalStateException`); it already covers the new grant once registered.
- Offline vs interactive: `TokenUtil.TOKEN_TYPE_OFFLINE` / `TokenUtil.isOfflineToken`; `TokenManager.verifyRefreshToken` accepts both types and signals problems as `OAuthErrorException(INVALID_GRANT, ...)`, which `RefreshTokenGrantType` converts to a 400 CORS error response. Raise the same error before invoking the refresh provider so nothing is minted and no 500 escapes.

**Verification**
- Existing OAuth tests live in `tests/base/src/test/java/org/keycloak/tests/oauth/` (`OfflineToken*Test`, `RefreshToken*Test`); test client request helpers in `tests/utils-shared/.../util/oauth/` (`RefreshRequest`, `JWTAuthorizationGrantRequest`, `AbstractOAuthClient`).
- Event assertions compare the access-token id prefix to factory `GRANT_SHORTCUT` (`.../testframework/events/EventAssertion.java`).
- `testsuite/.../oidc/AbstractWellKnownProviderTest.java` covers well-known metadata; whether it asserts an exact grant list is unverified.
