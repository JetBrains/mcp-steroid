# Hand-off note: dedicated offline-token refresh grant

## Goal
Add a new named grant type at the token endpoint that refreshes only long-lived (offline) refresh tokens. Presenting an ordinary (online) refresh token must fail with `invalid_grant` **before** any token is issued, as a normal protocol error (not a 500).

## What to imitate
The grant SPI lives in `server-spi-private/.../protocol/oidc/grants/`: `OAuth2GrantType` (interface: `getEventType()`, `getTokenParameterNames()`, `process(Context)`, optional `preProcess`, `isTokenAllowed`), `OAuth2GrantTypeFactory` (has `getId()` and `getShortcut()`), `OAuth2GrantTypeSpi`. Implementations sit in `services/.../protocol/oidc/grants/` — `RefreshTokenGrantType` / `RefreshTokenGrantTypeFactory` is the closest model; `OAuth2GrantTypeBase` is the shared base. Existing factories declare a `GRANT_SHORTCUT` constant (e.g. CIBA `ci`, device `dg`); pick a value not already used by any factory in that package tree.

## Changes and their dependencies
1. New grant type + factory beside `RefreshTokenGrantType`, with a unique id and shortcut. Grant-type id constants live in `core/.../OAuth2Constants.java` (see `TOKEN_EXCHANGE_GRANT_TYPE`, `DEVICE_CODE_GRANT_TYPE`, `CIBA_GRANT_TYPE` style); no offline-grant name exists yet, so you are choosing it.
2. Register the factory in `services/src/main/resources/META-INF/services/org.keycloak.protocol.oidc.grants.OAuth2GrantTypeFactory`. This registration alone makes `TokenEndpoint.checkGrantType()` (`session.getProvider(OAuth2GrantType.class, grantType)`) resolve it, and makes `OIDCWellKnownProvider.getGrantTypesSupported()` publish it — that method enumerates `OAuth2GrantType` provider factories (plus `implicit`), so metadata needs no separate edit.
3. Offline vs online detection: `TokenUtil.TOKEN_TYPE_OFFLINE` is the marker used in `protocol/oidc/refresh/*` (`AbstractRefreshTokenProvider`, `DefaultRefreshTokenProvider`), `TokenManager`, `UserSessionUtil`. Do the check early in `process()` and raise the standard CORS/OAuth error path used elsewhere in these grants.

## Easy to miss
- Shortcut/id uniqueness is enforced at boot in `DefaultTokenContextEncoderProviderFactory.postInit()` by comparing the sizes of `grantsByShortcuts` / `grantsToShortcuts`; a clash throws `IllegalStateException` at startup. Confirm that check actually fails on a duplicate — the task requires refusing to start.
- `AbstractWellKnownProviderTest` asserts an exact count (`assertEquals(10, …getGrantTypesSupported().size())`) plus a contains-list; both must be updated. Other well-known assertions exist under `tests/base/.../oid4vc/` and `authz` client `ServerConfiguration` / `UmaConfiguration`.

## Verification
Boot the server (duplicate-shortcut guard), fetch the well-known document and check the new grant appears, then exercise the token endpoint with an offline token (success) and an online refresh token (`invalid_grant`, no token minted).
