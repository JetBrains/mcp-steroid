# Hand-off: dedicated offline-token refresh grant

## Where things live (Keycloak-style layout)

- SPI: `server-spi-private/.../protocol/oidc/grants/OAuth2GrantType.java` (methods `process(Context)`, `getEventType()`, `getTokenParameterNames()`, `preProcess`, `isTokenAllowed`, `getSupportedMultivaluedRequestParameters`), `OAuth2GrantTypeFactory.java` (adds `getShortcut()`), `OAuth2GrantTypeSpi.java`.
- Implementations + factories: `services/src/main/java/org/keycloak/protocol/oidc/grants/` (plus `ciba/`, `device/` subpackages).
- Dispatch: `TokenEndpoint.checkGrantType()` resolves the grant purely by `session.getProvider(OAuth2GrantType.class, grantType)`; unknown ids yield `UNSUPPORTED_GRANT_TYPE`. No per-grant code in the endpoint is needed.
- Registration: `services/src/main/resources/META-INF/services/org.keycloak.protocol.oidc.grants.OAuth2GrantTypeFactory` — every factory is listed there; a new one must be added or it will not exist at runtime.
- Published metadata: `OIDCWellKnownProvider.getGrantTypesSupported()` derives the list from all registered `OAuth2GrantType` factory ids (plus `implicit`). Nothing to change there — appearing in metadata is automatic once registered.

## Model to imitate

`RefreshTokenGrantType` / `RefreshTokenGrantTypeFactory` (shortcut `"rt"`). `RefreshTokenGrantType.process` reads `refresh_token`, calls `tokenManager.verifyRefreshToken(...)`, picks a `RefreshTokenProvider` via `supports(RefreshTokenContext)`, then builds the response. Distinguishing offline vs. normal is done on the token's type: `TokenUtil.TOKEN_TYPE_OFFLINE` ("Offline"), as in `TokenManager` (~line 181, 353). For the rejection, use `OAuthErrorException.INVALID_GRANT` (TokenManager uses it pervasively) surfaced as a `CorsErrorResponseException` with 400 — `RefreshTokenGrantType` already maps `OAuthErrorException` that way. Check the token type *before* building/returning a response.

For the factory, the newest example is `JWTAuthorizationGrantTypeFactory`: `getId()` from an `OAuth2Constants` field, `getShortcut()`, `create`, empty init/postInit/close, optionally `EnvironmentDependentProviderFactory.isSupported` gated on a `Profile.Feature`. A new grant id constant belongs in `core/.../OAuth2Constants.java`.

## Shortcut uniqueness

`DefaultTokenContextEncoderProviderFactory.postInit` builds `grantsByShortcuts`/`grantsToShortcuts` from all factories and throws `IllegalStateException` if the map sizes differ — that is the existing start-up guard against duplicate ids/shortcuts. Taken shortcuts: `ac, rt, ci, dg, ag, cc, pc, pg, ro, te`. Pick something else; expose it as a `public static final String GRANT_SHORTCUT` (as `AuthorizationCode`/`RefreshToken`/`Ciba`/`Device` factories do) since tests assert on it.

## Easy to miss / verification

- `AbstractWellKnownProviderTest` (old arquillian testsuite, ~line 152) asserts an exact count `assertEquals(10, ...getGrantTypesSupported().size())` — it will break.
- Test client helpers live in `tests/utils-shared/.../util/oauth/`: `RefreshRequest` sets `grant_type=refresh_token`; `JWTAuthorizationGrantRequest` plus `AbstractOAuthClient.jwtAuthorizationGrantRequest/doJWTAuthorizationGrantRequest` show how to add a request type. A parallel request class + client method is likely needed.
- Existing offline tests: `tests/base/src/test/java/org/keycloak/tests/oauth/OfflineToken*Test.java`, `RefreshToken*Test.java`; shortcut assertions via `EventAssertion`/`hasAccessTokenId`. Unit test for the encoder maps: `services/src/test/java/org/keycloak/protocol/oidc/encode/DefaultTokenContextEncoderProviderTest.java`.
- Precedent commit for a whole new grant: "Experimental feature for JWT Authorization Grant" (Profile feature, OAuth2Constants, grant + factory, services file, tests, oauth client helper).
