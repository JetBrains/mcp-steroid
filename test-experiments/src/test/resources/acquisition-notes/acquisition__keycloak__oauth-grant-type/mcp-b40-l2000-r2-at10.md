**Hand-off: dedicated refresh grant for offline tokens**

**What to imitate.** Grants are an SPI: `OAuth2GrantType` and `OAuth2GrantTypeFactory` (`getId()` = the literal `grant_type` value, `getShortcut()` = unique short id stamped into tokens) in `server-spi-private/.../protocol/oidc/grants/`, SPI name `oauth2-grant-type` (`OAuth2GrantTypeSpi`). Implementations live in `services/.../protocol/oidc/grants/`, all extending `OAuth2GrantTypeBase`. The model to copy is `RefreshTokenGrantType` / `RefreshTokenGrantTypeFactory` (id `OAuth2Constants.REFRESH_TOKEN`, `GRANT_SHORTCUT = "rt"`).

**Changes and their dependencies.**
1. Add the new grant-type URN/name constant next to the other grant constants in `core/src/main/java/org/keycloak/OAuth2Constants.java` (e.g. alongside `DEVICE_CODE_GRANT_TYPE`, `CIBA_GRANT_TYPE`).
2. Add the grant class. Subclassing `RefreshTokenGrantType` is the low-risk path: `RefreshTokenContext` is a record typed on `RefreshTokenGrantType`, so an unrelated class won't fit the refresh pipeline.
3. Reject non-offline credentials **before** any token is built. `RefreshTokenGrantType.process` verifies the token via `tokenManager.verifyRefreshToken(...)` and then hands a `RefreshTokenContext` to a `RefreshTokenProvider`; offline-ness is expressed as `TokenUtil.TOKEN_TYPE_OFFLINE.equals(refreshToken.getType())` (see `AbstractRefreshTokenProvider`). Fail with the file's own error idiom — `event.error(...)` plus `CorsErrorResponseException(cors, OAuthErrorException.INVALID_GRANT, ..., BAD_REQUEST)` — not an exception that escapes as a 500.
4. Register the factory in `services/src/main/resources/META-INF/services/org.keycloak.protocol.oidc.grants.OAuth2GrantTypeFactory`.

**Easy to miss.**
- Metadata is derived, not hand-written: `OIDCWellKnownProvider.getGrantTypesSupported()` streams the registered `OAuth2GrantType` factories (plus `implicit`), so step 4 is what publishes it.
- `TokenEndpoint.checkGrantType()` resolves the provider by `getId()`; a mismatch yields "unsupported grant type".
- Shortcut uniqueness is enforced at boot in `DefaultTokenContextEncoderProviderFactory.postInit`, which throws `IllegalStateException` if two grants collide. Pick a shortcut not already used (`rt`, `ci`, `dg` are taken; check the remaining factories).

**Verify.** Server starts (no duplicate-shortcut failure); the new name appears in `grant_types_supported`; an offline refresh token returns a normal token response; a regular refresh token returns `invalid_grant` with no token issued. Test locations were not investigated.
