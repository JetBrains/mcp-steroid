## Hand-off: dedicated offline-token refresh grant

### What to imitate
The token endpoint's grants are a pluggable SPI: `OAuth2GrantType` (`server-spi-private/.../protocol/oidc/grants/OAuth2GrantType.java`), factories implement `OAuth2GrantTypeFactory` (same package; `getId()` + `getShortcut()`), SPI declared in `OAuth2GrantTypeSpi` (name `oauth2-grant-type`, internal). Implementations live in `services/.../protocol/oidc/grants/` and extend `OAuth2GrantTypeBase`.

Closest model: `RefreshTokenGrantType` + `RefreshTokenGrantTypeFactory` (id `OAuth2Constants.REFRESH_TOKEN`, `GRANT_SHORTCUT = "rt"`). Its `process()` shape: read `OAuth2Constants.REFRESH_TOKEN` from `formParams` (missing → `CorsErrorResponseException(INVALID_REQUEST, 400)`), fire `TokenRefreshContext` client policy, `tokenManager.verifyRefreshToken(...)`, build a `RefreshTokenContext`, select the highest-`order()` `RefreshTokenProvider` whose `supports(ctx)` is true, `refreshAccessToken(ctx)`, `checkAndBindMtlsHoKToken`, `TokenRefreshResponseContext`, then response sanitization via `AuthorizationDetailsProcessorManager`. `OAuthErrorException` is translated into a `CorsErrorResponseException` — use that same path for the rejection so it is a protocol error, not a 500.

### Changes and their dependencies
1. New grant class in `services/.../grants/`, extending `OAuth2GrantTypeBase`, mirroring the refresh flow but rejecting non-offline refresh tokens with `invalid_grant` **after** `verifyRefreshToken` and **before** selecting/invoking the `RefreshTokenProvider`. How offline-ness is determined from the verified token is not established in this record.
2. New factory with a new grant id (constant alongside `OAuth2Constants.REFRESH_TOKEN`) and a **new, unique** shortcut.
3. Register the factory in `services/src/main/resources/META-INF/services/org.keycloak.protocol.oidc.grants.OAuth2GrantTypeFactory`.
4. Advertise the grant in discovery metadata — the class producing `grant_types_supported` was not located in this record.
5. Also consider the other interface members: `getEventType()`, duplicated/token parameter names, `preProcess`, and the "is token from this grant allowed for this request" hook.

### Easy to miss
Shortcut uniqueness is enforced at startup in `DefaultTokenContextEncoderProviderFactory.postInit` by comparing the sizes of `grantsByShortcuts`/`grantsToShortcuts`; a clash throws `IllegalStateException`. Its lazy lookup helpers also re-scan factories, so a duplicate id or shortcut breaks token stamping.

### Verify
Server boots (the uniqueness guard), offline credential returns a token, ordinary refresh token returns `invalid_grant`, and the grant appears in discovery. Existing tests covering these were not identified.
