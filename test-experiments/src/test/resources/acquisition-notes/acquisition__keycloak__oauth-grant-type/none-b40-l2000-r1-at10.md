## Hand-off note: dedicated refresh operation for long-lived credentials

**Repository**: Keycloak. Grant types at the token endpoint are pluggable providers behind the SPI `oauth2-grant-type` (`server-spi-private/.../protocol/oidc/grants/OAuth2GrantTypeSpi.java`, internal SPI).

**What to imitate**
- `services/.../protocol/oidc/grants/RefreshTokenGrantType.java` — the existing renewal grant: reads `OAuth2Constants.REFRESH_TOKEN` from `formParams`, triggers client policies, calls `tokenManager.verifyRefreshToken(...)`, builds a `RefreshTokenContext`, picks the highest-ordered `RefreshTokenProvider` that `supports(...)`, then `refreshAccessToken`. Errors are surfaced as `CorsErrorResponseException(cors, <OAuthErrorException code>, desc, 400)` after `event.error(...)` — use this pattern for the "invalid grant" rejection so it is a protocol error, not a 500.
- `services/.../protocol/oidc/grants/RefreshTokenGrantTypeFactory.java` — minimal factory: `getId()` (the grant-type wire name, from `OAuth2Constants`), `getShortcut()` (`"rt"`), `create(session)`, empty `init/postInit/close`. Your new grant needs its own id and its own distinct shortcut.
- Common plumbing lives in `services/.../grants/OAuth2GrantTypeBase.java` (`setContext`, `createTokenResponseBuilder`, mTLS binding). Note it stamps `Constants.GRANT_TYPE` from `context.getGrantType()` onto the client session context and references `TokenUtil.TOKEN_TYPE_OFFLINE` — that is the likely hook for distinguishing long-lived from interactive credentials. Verify the check runs *before* any token is created.

**Changes and their dependencies**
1. New grant + factory (as above); a new grant-name constant probably belongs in `core/.../OAuth2Constants.java`.
2. Register the factory wherever `RefreshTokenGrantTypeFactory` is registered (registration file not inspected).
3. Publish the operation in discovery metadata: `services/.../protocol/oidc/OIDCWellKnownProvider.java` plus `core/.../protocol/oidc/representations/OIDCConfigurationRepresentation.java` (contents unexamined). `OAuth2WellKnownProviderFactory` also exists.
4. Shortcut uniqueness: `OAuth2GrantTypeFactory.getShortcut()` javadoc already requires uniqueness, but the record does not show any code enforcing it — locate or add a startup-time check that fails fast on duplicates. `TokenContextEncoderProvider` (used by `OAuth2GrantTypeBase`) is a plausible place where shortcuts are consumed.

**Easy to miss**: `OAuth2GrantType.isTokenAllowed` and `services/managers/GrantTypeEndpointRestrictionValidator` may need to know about the new grant.

**Verification**: `testsuite/integration-arquillian/tests/base/.../oidc/OIDCWellKnownProviderTest.java` for metadata; add tests covering success with a long-lived credential and invalid-grant rejection of an interactive one; a startup test for duplicate shortcuts.
