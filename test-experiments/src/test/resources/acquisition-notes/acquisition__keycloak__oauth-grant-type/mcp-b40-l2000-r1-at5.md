## Hand-off: dedicated offline refresh grant at the token endpoint

**Where the machinery lives**

- SPI: `server-spi-private/.../protocol/oidc/grants/OAuth2GrantType.java`, `OAuth2GrantTypeFactory.java`, `OAuth2GrantTypeSpi.java`.
- All implementations sit in `services/src/main/java/org/keycloak/protocol/oidc/grants/`: `OAuth2GrantTypeBase` (shared base), plus `AuthorizationCode`, `ClientCredentials`, `ResourceOwnerPasswordCredentials`, `JWTAuthorization`, `TokenExchange`, `Permission`, `PreAuthorizedCode`, `device/DeviceGrantType`, `ciba/CibaGrantType`, and `RefreshTokenGrantType` (+ `RefreshTokenGrantTypeFactory`).
- Registration: `services/src/main/resources/META-INF/services/org.keycloak.protocol.oidc.grants.OAuth2GrantTypeFactory` — the new factory must be added there (its current contents were not read).

**What to imitate**

Model the new grant on `RefreshTokenGrantType`/`RefreshTokenGrantTypeFactory` (their bodies were not inspected — read them first; the refresh logic should be reused, not duplicated). The interface requires `getEventType()`, `getTokenParameterNames()`, `process(Context)`; optional `preProcess`, `getSupportedMultivaluedRequestParameters`, `isTokenAllowed`. `Context` hands you session, realm, client, formParams, `EventBuilder event`, `Cors cors` and `tokenManager` — use `event`/error path so the "not an offline token" case surfaces as an `invalid_grant` protocol response, and perform that check before any token is issued.

**Dependencies / easy to miss**

1. The factory's `getShortcut()` must be new and unique. `services/.../protocol/oidc/encode/DefaultTokenContextEncoderProviderFactory.postInit` builds shortcut↔grant-id maps over all factories and throws `IllegalStateException` on a size mismatch, so a clash aborts startup; the same class also lazily refreshes those maps by shortcut/id.
2. Grant-type id constants live in `core/src/main/java/org/keycloak/OAuth2Constants.java` (e.g. `OFFLINE_ACCESS`, `TOKEN_EXCHANGE_GRANT_TYPE`, `CIBA_GRANT_TYPE`); add the new identifier there.
3. Published metadata comes from `services/.../protocol/oidc/OIDCWellKnownProvider.java`; how it derives `grant_types_supported` (static list vs. factory enumeration) is unknown — check before assuming it picks the new grant up automatically.

**Verify**: server starts (no duplicate-shortcut failure); the new grant appears in the well-known document; an offline token renews, an ordinary refresh token returns `invalid_grant`.
