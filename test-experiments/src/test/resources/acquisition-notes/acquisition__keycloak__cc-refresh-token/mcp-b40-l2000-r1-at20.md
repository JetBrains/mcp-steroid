## Hand-off note: forbid refresh token from client credentials grant under `strict`

**Shape of the feature.** A security profile is a JSON file in `services/src/main/resources` (`none-`, `lax-`, `strict-security-profile.json`); `DefaultSecurityProfileProviderFactory` reads `<name>.json` (default `none-security-profile`) from classpath/`conf` and resolves its `client-profiles`/`client-policies` names into the global JSONs. `strict-security-profile.json` points at `keycloak-default-client-profiles.json` + `keycloak-strict-client-policies.json`. So the rule is expressed as a client-policy executor added to a global profile used by the strict policies (the OAuth 2.1 confidential-client profile, `oauth-2-1-for-confidential-client`, lives in `keycloak-default-client-profiles.json` and is referenced from the strict and lax policy files) — no code change in the profile machinery itself.

**What to imitate.** `services/.../clientpolicy/executor/RejectResourceOwnerPasswordCredentialsGrantExecutor(+Factory)` is the closest template: `Configuration` with `@JsonProperty("auto-configure")`, `executeOnEvent` switching on `REGISTER`/`UPDATE` to `autoConfigure(...)` then `validate(...)` on `getProposedClientRepresentation()`, throwing `ClientPolicyException(OAuthErrorException.INVALID_CLIENT_METADATA, ...)`. For the "update that omits the flag but the stored client has it on" case, copy `ConsentRequiredExecutor.beforeUpdate(getTargetClient(), proposedClient)`: on UPDATE it consults `ClientCRUDContext.getTargetClient()` (null on REGISTER) and only skips validation when the proposed value is absent *and* the stored value is compliant.

**The flag.** `OIDCConfigAttributes.USE_REFRESH_TOKEN_FOR_CLIENT_CREDENTIALS_GRANT = "client_credentials.use_refresh_token"`, accessed via `OIDCAdvancedConfigWrapper.isUseRefreshTokenForClientCredentialsGrant()/set...` (default false), e.g. `OIDCAdvancedConfigWrapper.fromClientRepresentation(rep)`.

**Easy to miss.**
- Register the new factory in `services/src/main/resources/META-INF/services/org.keycloak.services.clientpolicy.executor.ClientPolicyExecutorProviderFactory`.
- Executor id string must be added to the profile JSON; ids also appear in `js/apps/admin-ui/src/context/server-info/__tests__/mock.json` (existing ids are listed there).
- Both admin REST and dynamic registration flow through the same REGISTER/UPDATE events (`AdminClientRegister/UpdateContext`, `DynamicClientRegister/UpdateContext`) — one executor covers both.
- Confidential-OIDC-only scoping comes from which profile you put the executor in.
- Docs `docs/guides/securing-apps/partials/oidc/oauth21-support.adoc` describes the OAuth 2.1 profiles; release notes/upgrading pages mention security profiles.

**Verification.** `DefaultSecurityProfileProverFactoryTest` (services module) loads all three profile JSONs and fails on unknown executor ids. `OAuth2_1ConfidentialClientTest` (arquillian) shows the create-by-admin / fail-dynamically pattern with `setupPolicyOAuth2_1ConfidentialClientForAllClient()`. New-style tests: `tests/base/.../securityprofile/LaxSecurityProfileTest` (uses `@KeycloakIntegrationTest` with a `KeycloakServerConfig` setting the profile) — no strict-profile test exists yet; that is the gap to fill.
