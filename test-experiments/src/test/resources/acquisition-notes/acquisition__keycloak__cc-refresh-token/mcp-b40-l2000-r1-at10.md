**Hand-off: reject refresh tokens from client credentials grant under the `strict` security profile**

What the feature is built from
- Profiles live in `services/src/main/resources/{none,lax,strict}-security-profile.json`. `strict` is only three fields: `name`, `client-profiles: keycloak-default-client-profiles`, `client-policies: keycloak-strict-client-policies`; those two JSON files sit in the same directory. The provider side is `server-spi-private/.../securityprofile/*` and `services/.../securityprofile/DefaultSecurityProfileProvider(+Factory)`, registered through `META-INF/services/org.keycloak.securityprofile.SecurityProfileProviderFactory`.
- Client policy executors live in `services/src/main/java/org/keycloak/services/clientpolicy/executor/` and must be registered in `services/src/main/resources/META-INF/services/org.keycloak.services.clientpolicy.executor.ClientPolicyExecutorProviderFactory`.

What to imitate
- `RejectResourceOwnerPasswordCredentialsGrantExecutor` (+`...Factory`) is the closest template: an `executeOnEvent` switch that, on `REGISTER`/`UPDATE`, casts to `ClientCRUDContext`, runs `autoConfigure(rep)` then `validate(rep)`, and fails with `ClientPolicyException(OAuthErrorException.INVALID_CLIENT_METADATA, ...)`. Its `Configuration` holds a single `@JsonProperty("auto-configure")` flag — that is the mechanism for "created without mentioning it ends up switched off".
- For an attribute-backed flag, follow the executors that use `OIDCAdvancedConfigWrapper` (`DPoPBindEnforcerExecutor`, `SecureLogoutExecutor`, `PKCEEnforcerExecutor`). The attribute is `OIDCConfigAttributes.USE_REFRESH_TOKEN_FOR_CLIENT_CREDENTIALS_GRANT` (`client_credentials.use_refresh_token`) in `server-spi-private/.../protocol/oidc/OIDCConfigAttributes.java`.

Dependencies / easy to miss
- `ClientCRUDContext` exposes both `getProposedClientRepresentation()` and `getTargetClient()` (null on REGISTER). An update that omits the attribute must be judged against the target client — the ROPC template only reads the proposed rep, so it is not sufficient here.
- Confidential-OIDC-only scoping must be handled explicitly; a `confidential-client` executor id exists in the shipped profiles but its code was not reviewed.
- Registering the executor is not enough: it must be wired into the profile/policy JSONs so `strict` picks it up out of the box; `keycloak-strict-client-policies.json` and the tail of `keycloak-default-client-profiles.json` were not read, so confirm which profile `strict` actually enables.

Verification
- `tests/base/src/test/java/org/keycloak/tests/securityprofile/LaxSecurityProfileTest.java` is the only test there; mirror it for a strict test covering admin REST and dynamic client registration create/update, the omit-on-update case, and the default-off case. Also see `services/src/test/.../DefaultSecurityProfileProverFactoryTest`. Ensure no-profile servers are unaffected.
