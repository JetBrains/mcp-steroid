**Hand-off note — enforce "no refresh token from client credentials" under the `strict` security profile**

**Where the feature lives**
- Security profile SPI: `server-spi-private/src/main/java/org/keycloak/securityprofile/` (`SecurityProfileProvider`, `SecurityProfileProviderFactory`, `SecurityProfileSpi`); implementation in `services/src/main/java/org/keycloak/services/securityprofile/Default*`, registered via `services/src/main/resources/META-INF/services/org.keycloak.securityprofile.SecurityProfileProviderFactory`. Representation: `core/.../representations/idm/SecurityProfileConfiguration.java`.
- Profiles are shipped as `services/src/main/resources/{none,lax,strict}-security-profile.json`. `strict-security-profile.json` only names two resources: `client-profiles: keycloak-default-client-profiles` and `client-policies: keycloak-strict-client-policies`, both `.json` files in the same resources directory. So `strict` behaviour is expressed entirely as a global client profile + policy; the intended change is a new client-policy executor plus its declaration in those JSONs (the strict policies file's contents were not inspected — check which profile(s) it activates before deciding where to hook in).

**What to imitate**
- `services/src/main/java/org/keycloak/services/clientpolicy/executor/RejectImplicitGrantExecutor{,Factory}.java` and `RejectResourceOwnerPasswordCredentialsGrantExecutor{,Factory}.java` — closest analogues. Factory contract: `server-spi-private/.../services/clientpolicy/executor/ClientPolicyExecutorProviderFactory.java`; events to handle come from `server-spi/.../services/clientpolicy/ClientPolicyEvent.java` (this is the single funnel that covers both admin REST and dynamic client registration, and register vs update).
- In `keycloak-default-client-profiles.json`, executors appear as `{"executor": "...", "configuration": {...}}`; `reject-implicit-grant` uses `"auto-configure": true`. Use the same `auto-configure` idiom to satisfy "created without mentioning it ⇒ ends up off".

**The attribute**
Constant lives in `server-spi-private/.../protocol/oidc/OIDCConfigAttributes.java` (`use.refresh.tokens.for.client.credentials.grant`); read/write it through `services/.../protocol/oidc/OIDCAdvancedConfigWrapper.java` rather than raw attribute strings.

**Easy to miss**
- An update request that omits the attribute must still fail if the stored client has it on — read the existing client, not just the incoming representation.
- Restrict to confidential OIDC clients (public/non-OIDC untouched); `none`/`lax` profiles must be unaffected.
- New executor factories need a provider-registration entry (the exact `META-INF/services` file for executor factories was not inspected).

**Verification**
`tests/base/src/test/java/org/keycloak/tests/securityprofile/` holds profile-level tests (`LaxSecurityProfileTest`); add/extend a strict counterpart there. Factory-level unit test pattern: `services/src/test/java/org/keycloak/services/securityprofile/DefaultSecurityProfileProverFactoryTest.java`.
