## Hand-off note

**Where the pieces live**

- Security profiles are declared as small JSON files in `services/src/main/resources/`: `strict-security-profile.json`, `lax-security-profile.json`, `none-security-profile.json`. Each names a client-profiles set and a client-policies set: `strict` → `keycloak-default-client-profiles` + `keycloak-strict-client-policies` (`none` has `null` policies). Only the `src/main/resources` copies are sources; the `services/target/classes/*` duplicates are build output.
- The SPI is `server-spi-private/.../keycloak/securityprofile/` (`SecurityProfileSpi` — internal, name `security-profile`; `SecurityProfileProvider` exposing `getDefaultClientProfiles()` / `getDefaultClientPolicies()`; `SecurityProfileProviderFactory`), implemented by `services/.../services/securityprofile/DefaultSecurityProfileProvider(+Factory)`. The provider javadoc states the mechanism is currently expressed entirely through client policies.
- Client-policy machinery: `services/.../services/clientpolicy/` (`DefaultClientPolicyManager`, `ClientPoliciesUtil`, `ClientPolicy`, `ClientProfile`) with executors in `.../clientpolicy/executor/` — imitate an existing simple one such as `ConsentRequiredExecutor` or `FullScopeDisabledExecutor`. SPI-side contracts (`ClientPolicyContext`, `ClientPolicyEvent`, `ClientPolicyVote`, `ClientPolicyException`) are in `server-spi`/`server-spi-private`.
- The setting to police is `OIDCConfigAttributes.USE_REFRESH_TOKEN_FOR_CLIENT_CREDENTIALS_GRANT` (`"client_credentials.use_refresh_token"`, in `server-spi-private`), read via `OIDCAdvancedConfigWrapper`, which defaults it to `"false"` when absent — so "created without mentioning it ends up off" needs no extra work.

**Shape of the change (dependencies)**

A new executor + its factory (registered as a provider service), then referenced from the client profile/policy definitions that `strict` pulls in — the `keycloak-strict-client-policies` and `keycloak-default-client-profiles` resources. Changing only the executor without wiring it into the strict definitions gives no out-of-the-box enforcement; changing only the JSON gives an unknown-executor failure.

**Easy to miss**

- Both the admin REST path and dynamic client registration must be covered; that means handling every relevant create/update event of `ClientPolicyEvent`, not just one (the event constants were not inspected — check them).
- An update representation that omits the attribute must be rejected when the *stored* client already has it on, so the executor must consult the existing client, not just the incoming representation.
- Restrict the check to confidential OIDC clients; leave `none`/`lax` behaviour untouched.

**Verification**

Follow `tests/base/src/test/java/org/keycloak/tests/securityprofile/LaxSecurityProfileTest.java` for a profile-scoped integration test (a strict counterpart was not observed). `services/src/test/.../securityprofile/DefaultSecurityProfileProverFactoryTest` covers profile loading. Existing tests that set the attribute to `true` (e.g. `tests/base/.../oauth/RefreshTokenTest`, `OfflineToken*Test`, arquillian `ServiceAccountTest`, `AuthzClientCredentialsTest`) must keep passing without a security profile.
