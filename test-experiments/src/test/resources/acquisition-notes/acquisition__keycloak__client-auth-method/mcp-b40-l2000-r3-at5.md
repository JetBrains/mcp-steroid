# Hand-off: self-signed-certificate client authenticator

## What to imitate
Two siblings live in `services/src/main/java/org/keycloak/authentication/authenticators/client/`:

* `X509ClientAuthenticator` (`PROVIDER_ID = "client-x509"`) — closest functional model. It extends `AbstractClientAuthenticator`, obtains the chain from the `X509ClientCertificateLookup` provider (`context.getSession().getProvider(...)`, `getCertificateChain(context.getHttpRequest())`), resolves `client_id` from decoded form data, then query params, then the `client_id` session attribute, calls `context.getEvent().client(...)`/`setClient`, fails with `CLIENT_NOT_FOUND`/`CLIENT_DISABLED`, and `context.attempted()` when no cert is present. It then goes on to `OIDCAdvancedConfigWrapper` and `CertificateValidator` plus the `x509.subjectdn` / `x509.casubjectdn` / `x509.allow.regex.pattern.comparison` attributes — this trust-chain + subject-DN part is exactly what the new authenticator must NOT do; it should instead compare the presented certificate byte-for-byte with the certificate stored on the client.
* `AttestationBasedClientAuthenticator` is the most recently added authenticator; its footprint shows every registration point a new one needs.

## Changes and their dependencies
1. New authenticator class next to the two above, with its own provider id.
2. Register the factory in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory` (both existing authenticators are listed there).
3. Add the auth-method constant to `org.keycloak.protocol.oidc.OIDCLoginProtocol` alongside `TLS_CLIENT_AUTH` / `ATTEST_JWT_CLIENT_AUTH` (~lines 125-136). No `self_signed_tls_client_auth`/`SELF_SIGNED` string exists anywhere yet.
4. Surface it in discovery via `OIDCWellKnownProvider.getClientAuthMethodsSupported()` (the only place that method exists) — this is what dynamic registration keys off.
5. Add the provider id next to every `"client-x509"` entry under the `secure-client-authenticator` executor in `services/src/main/resources/keycloak-default-client-profiles.json` (fapi-1-baseline, fapi-1-advanced, fapi-2-security-profile, fapi-2-message-signing, fapi-2-dpop-*, oauth-2-1-for-confidential-client). Executor logic lives in `services/.../clientpolicy/executor/SecureClientAuthenticatorExecutor(Factory)`.

## Easy to miss
* Where the client's certificate is stored/read (attribute name, config wrapper) was not established — determine it from the truncated tail of `X509ClientAuthenticator` and `OIDCAdvancedConfigWrapper`.
* `TokenManager` references the attestation authenticator; check whether similar wiring is needed.
* Provider-enumeration tests (`tests/base/.../admin/authentication/ProvidersTest`, `InitialFlowsTest`), admin-console `js/apps/admin-ui/src/clients/credentials/Credentials.tsx` and its server-info mocks, and `DefaultAuthenticationFlows` all hard-code `client-x509`.

## Verify
Existing coverage to extend: FAPI1Test / FAPI2Test / AbstractFAPI2Test / FAPICIBATest, `ClientPoliciesExecutorTest`, `OIDCClientRegistrationTest`, and `OIDCAuthorizationMetadataTest` (discovery list). Must-have cases: exact stored cert authenticates; any different cert — including a re-issued one with identical subject DN and key — is refused; no trust store consulted.
