## Hand-off note: self-signed-certificate client authentication

### What to imitate
`services/src/main/java/org/keycloak/authentication/authenticators/client/X509ClientAuthenticator.java` (`PROVIDER_ID = "client-x509"`) is the template. Copy its useful half: obtain the chain from the `X509ClientCertificateLookup` SPI provider (`provider.getCertificateChain(context.getHttpRequest())`, null/empty → `context.attempted()`), resolve `client_id` from decoded form data, then query params, then the session attribute `"client_id"`, then `getClientByClientId`, `context.getEvent().client(...)`, `setClient`, and the enabled check. Drop everything after that: no `CertificateValidator`, no `ATTR_SUBJECT_DN`/`ATTR_CA_SUBJECT_DN` matching, no trust store.

The stored certificate lives in the client's credential attributes; read it via `CertificateInfoHelper.getCertificateFromClient(client, prefix)` (see `services/src/main/java/org/keycloak/services/util/CertificateInfoHelper.java`); `JWTClientAuthenticator` uses prefix `"jwt.credential"` / attr `jwt.credential.certificate`. Beware that helper returns a JWKS-derived representation when the client has `use.jwks.string` enabled — that path yields no certificate. Compare the full DER/encoded certificate, not subject DN or public key, so a re-issued cert with identical DN and key is rejected.

New provider class goes in the same package and must be listed in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory`.

### Dependent changes
- Discovery is automatic: `OIDCWellKnownProvider.getClientAuthMethodsSupported()` flattens `ClientAuthenticatorFactory.getProtocolAuthenticatorMethods(OIDCLoginProtocol.LOGIN_PROTOCOL)`. Implement that method returning the new method name; add a constant next to `OIDCLoginProtocol.TLS_CLIENT_AUTH` ("tls_client_auth", line ~129).
- Dynamic registration mapping lives in `services/.../clientregistration/oidc/DescriptionConverter.java` and `core/.../representations/oidc/OIDCClientRepresentation.java`, which already handle `tls_client_auth`.
- Add the new provider id alongside every `"client-x509"` entry in `secure-client-authenticator` → `allowed-client-authenticators` in `services/src/main/resources/keycloak-default-client-profiles.json` (~7 occurrences; the copy under `target/classes` is build output).
- Check the `client-x509`-specific branches in `services/.../validation/DefaultClientValidationProvider.java:609` and `services/.../clientpolicy/executor/TlsClientAuthCASubjectDNExecutor.java:88` — the new type must not inherit subject-DN requirements. `DefaultAuthenticationFlows:517` references `client-x509`; unknown whether default flows need touching.
