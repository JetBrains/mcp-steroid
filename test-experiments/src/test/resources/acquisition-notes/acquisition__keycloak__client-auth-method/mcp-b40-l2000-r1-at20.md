# Hand-off note: self-signed X.509 client authentication

## Goal
Add a new client authenticator that authenticates a client iff the certificate presented in the mutual-TLS handshake is byte-for-byte identical to the certificate stored in that client's credential config. No trust store, no CA chain, no subject-DN matching.

## What to imitate
- `services/.../authentication/authenticators/client/X509ClientAuthenticator.java` (id `client-x509`) — closest model. Reuse its client resolution logic (client_id from form data, then query params, then session attribute; then `getClientByClientId`, `context.getEvent().client(...)`, `context.setClient(...)`, enabled check) and its use of `X509ClientCertificateLookup` (`provider.getCertificateChain(context.getHttpRequest())`) to get the presented chain; compare only position 0. Do **not** carry over `ATTR_SUBJECT_DN`/`ATTR_CA_SUBJECT_DN`/regex handling or `CertificateValidator`.
- `JWTClientAuthenticator` shows the stored-certificate convention: attribute prefix `jwt.credential`, cert attribute `jwt.credential.certificate`. Read the stored cert via `org.keycloak.services.util.CertificateInfoHelper.getCertificateFromClient(client, prefix)`; `org.keycloak.common.util.PemUtils` has `decodeCertificate` / `encodeCertificate`.
- Both extend `AbstractClientAuthenticator`; the factory contract is `org.keycloak.authentication.ClientAuthenticatorFactory`.

## Changes and their dependencies
1. New authenticator + factory; register the factory FQN in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory`.
2. Add an ALTERNATIVE execution for the new provider id in `DefaultAuthenticationFlows.clientAuthFlow` (`server-spi-private`), next to `client-secret`/`client-jwt`/`client-x509`, with its own priority — `ClientAuthenticationFlow` only runs executions present in the realm's `clients` flow and then matches the succeeding authenticator against `client.getClientAuthenticatorType()`. Existing realms may need migration (`MigrateTo*` / `migrateFlows` pattern exists; not verified for this case).
3. Discovery: `getProtocolAuthenticatorMethods` must return the new OIDC auth-method name; add the constant beside `TLS_CLIENT_AUTH` in `OIDCLoginProtocol`. `OIDCWellKnownProvider` builds `token_endpoint_auth_methods_supported` from the registered factories, so it should pick it up automatically. Dynamic registration resolves the name via `AuthorizeClientUtil.findClientAuthenticatorForOIDCAuthMethod` used by `DescriptionConverter`.
4. Security profiles: add the new id to `allowed-client-authenticators` in `services/src/main/resources/keycloak-default-client-profiles.json` for the profiles that already list `client-x509`: fapi-1-baseline, fapi-1-advanced, fapi-2-security-profile, fapi-2-message-signing, oauth-2-1-for-confidential-client, fapi-2-dpop-security-profile, fapi-2-dpop-message-signing.

## Easy to miss
- Code keyed on `client-x509` that must **not** apply: `DefaultClientValidationProvider.validateX509Credentials` (CA-DN warnings) and `TlsClientAuthCASubjectDNExecutor`.
- Admin UI `js/apps/admin-ui/src/clients/credentials/Credentials.tsx` branches on `clientAuthenticatorType`; the new type needs a panel decision (the stored-cert UI is `SignedJWT`/keys, the `X509` panel is DN-based).
- Server-info mock JSONs under admin-ui `__tests__` list authenticators and may need updating.

## Verification
- Follow `tests/base/src/test/java/org/keycloak/tests/client/AbstractMutualTLSClientTest.java` (+ `MutualTLSClientTest`, `MutualTLSClientDedicatedStoreTest`): `@InjectRealm` with a `RealmConfig`, `@InjectOAuthClient`, an SSL-configured `CloseableHttpClient`, `ManagedCertificates`. Add cases: success with the exact stored cert; failure with a re-issued cert having the same subject DN and same key.
- Also exercise discovery contents and client policy acceptance; older `testsuite/integration-arquillian` FAPI/client-policy tests enumerate `client-x509` and may need parallel entries.
