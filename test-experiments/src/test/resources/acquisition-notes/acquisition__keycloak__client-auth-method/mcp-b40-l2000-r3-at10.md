# Hand-off: self-signed X509 client authenticator

## Goal
New `ClientAuthenticator` that authenticates a client at the token endpoint iff the TLS-presented certificate is byte-identical to the certificate already stored on the client, with no trust-store/CA-chain check and no subject-DN matching. Any different cert (even same DN + same key, re-issued) must fail.

## What to imitate
- `services/src/main/java/org/keycloak/authentication/authenticators/client/X509ClientAuthenticator.java` — closest model. Extends `AbstractClientAuthenticator`; `PROVIDER_ID = "client-x509"`; obtains the chain via `session.getProvider(X509ClientCertificateLookup.class).getCertificateChain(context.getHttpRequest())`; resolves `client_id` from form data, then query params, then session attribute; handles missing client_id / unknown client / disabled client; calls `context.attempted()` when no cert is present. Its DN/CA logic (`ATTR_SUBJECT_DN`, `ATTR_CA_SUBJECT_DN`, regex comparison, `CertificateValidator`, `OIDCAdvancedConfigWrapper`) is exactly what must NOT be carried over.
- `AttestationBasedClientAuthenticator` in the same package is the most recently added authenticator; use it as the checklist of registration points.
- Stored client certificate access: `services/src/main/java/org/keycloak/services/util/CertificateInfoHelper.java` (used by `ClientAttributeCertificateResource`, `ClientPublicKeyLoader`, `DescriptionConverter`). Attribute prefixes follow the `client-jwt` pattern (`jwt.credential`); confirm which prefix the admin console X509 credential upload writes.

## Changes and their dependencies
1. New authenticator class + `PROVIDER_ID` in `services/.../authenticators/client/`.
2. Register it in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory`.
3. Add an auth-method constant next to `TLS_CLIENT_AUTH` / `ATTEST_JWT_CLIENT_AUTH` in `OIDCLoginProtocol.java` (lines ~125-136) and return it from `getProtocolAuthenticatorMethods(OIDCLoginProtocol.LOGIN_PROTOCOL)`. This alone makes it appear in discovery (`OIDCWellKnownProvider.getClientAuthMethodsSupported()` enumerates factories) and makes dynamic registration work (`AuthorizeClientUtil.findClientAuthenticatorForOIDCAuthMethod`).
4. Add the new provider id alongside `"client-x509"` in every `secure-client-authenticator` executor block of `services/src/main/resources/keycloak-default-client-profiles.json` (fapi-1-baseline/advanced, fapi-2-*, oauth-2-1-for-confidential-client).

## Easy to miss
- Admin console `js/apps/admin-ui/src/clients/credentials/Credentials.tsx` hard-codes ids (`clientAuthenticatorType === "client-x509"` → `<X509 />`); the new id needs a branch to expose the cert UI.
- `DefaultClientValidationProvider` and `TlsClientAuthCASubjectDNExecutor` reference `X509ClientAuthenticator` constants — check whether they should also apply to (or explicitly skip) the new id.
- Discovery lists the methods for token, introspection and revocation endpoints from the same list.

## Verification
Follow existing patterns in `tests/base/.../admin/authentication/ProvidersTest.java`, `InitialFlowsTest.java` (provider listings), `OIDCAuthorizationMetadataTest` / `OIDCClientRegistrationTest` (discovery + registration), and the FAPI tests. Cover: identical cert accepted; different cert with same DN and same key rejected.
