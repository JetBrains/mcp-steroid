# Hand-off note: self-signed-certificate client authenticator

## Goal
Add a client authenticator that authenticates a client when the certificate presented in the mutual-TLS handshake is byte-for-byte identical to the certificate stored in the client's credential configuration. No trust store, no CA chain, no subject-DN matching.

## What to imitate
- `services/.../authentication/authenticators/client/X509ClientAuthenticator.java` (extends `AbstractClientAuthenticator`, `PROVIDER_ID = "client-x509"`). Reuse its front half verbatim: obtain the cert chain via `X509ClientCertificateLookup` from the session (missing SPI → log + return; `GeneralSecurityException` or empty chain → `context.attempted()`), resolve `client_id` from form data, then query params, then the session attribute, `context.setClient`, checks for unknown/disabled client. Drop everything after that (`ATTR_SUBJECT_DN`, `ATTR_CA_SUBJECT_DN`, `ATTR_ALLOW_REGEX_PATTERN_COMPARISON`, `CertificateValidator`, the custom-OID/`X500Principal` machinery).
- `JWTClientAuthenticator` shows the stored-certificate convention: `CERTIFICATE_ATTR = "jwt.credential.certificate"` under attribute prefix `jwt.credential`. Read the stored cert with `org.keycloak.services.util.CertificateInfoHelper.getCertificateFromClient(client, prefix)`; `org.keycloak.common.util.PemUtils` (`decodeCertificate`, `encodeCertificate`) is available for PEM handling. Compare encoded bytes, not subject/key — a re-issued cert with identical DN and key must fail.
- `getProtocolAuthenticatorMethods(String loginProtocol)` is the hook that feeds discovery; `OIDCLoginProtocol` holds the method-name constants (`TLS_CLIENT_AUTH`, `PRIVATE_KEY_JWT`, …) — add one for the new method. `OIDCWellKnownProvider` builds `token_endpoint_auth_methods_supported` from the registered `ClientAuthenticatorFactory` providers (around lines 155-165), so discovery and dynamic registration follow automatically once the factory returns the new method name.

## Wiring (order matters)
1. New authenticator class + `PROVIDER_ID` and auth-method constant.
2. Register the class in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory`.
3. Add an ALTERNATIVE execution in `DefaultAuthenticationFlows.clientAuthFlow` (`server-spi-private`), following the `client-x509` block at priority 40 — pick a free priority. Note `addFlows`/`migrateFlows` only create the flow when absent, so pre-existing realms may need a migration step (whether one is required was not established).
4. Add the new id to `allowed-client-authenticators` lists in `services/src/main/resources/keycloak-default-client-profiles.json` wherever `client-x509` appears (fapi-1-baseline, fapi-2-dpop-message-signing, and ~6 more occurrences).

## Easy to miss
- `TlsClientAuthCASubjectDNExecutor` and `DefaultClientValidationProvider.validateX509Credentials` are keyed on `X509ClientAuthenticator.PROVIDER_ID`; the new id must NOT be added there (no CA DN applies).
- `ClientIdMetadataDocumentExecutor.ALLOWED_ALGORITHMS` lists allowed auth methods — decide whether the new method belongs.
- Admin UI: `js/apps/admin-ui/src/clients/credentials/Credentials.tsx` switches panels on `clientAuthenticatorType`; `client-x509` renders `<X509 />`. A self-signed authenticator likely wants the certificate-upload panel, not the X509 DN panel.

## Verification
Follow `tests/base/src/test/java/org/keycloak/tests/client/AbstractMutualTLSClientTest.java` / `MutualTLSClientTest` / `MutualTLSClientDedicatedStoreTest`. Cover: matching cert succeeds; different cert and re-issued same-DN/same-key cert fail; the method appears in well-known; FAPI/OAuth2.1 profiles accept the client (see the `client-x509` usages in `testsuite/.../client/FAPI*Test.java`, `OAuth2_1ConfidentialClientTest`, `OIDCClientRegistrationTest`).
