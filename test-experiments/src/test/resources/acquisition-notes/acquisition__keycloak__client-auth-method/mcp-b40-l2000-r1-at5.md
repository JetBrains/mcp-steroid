## Hand-off: self-signed-certificate client authenticator

**What to imitate.** The model is `services/src/main/java/org/keycloak/authentication/authenticators/client/X509ClientAuthenticator.java` (`PROVIDER_ID = "client-x509"`), which extends `AbstractClientAuthenticator` in the same package; the SPI interfaces are `ClientAuthenticator` / `ClientAuthenticatorFactory` in `server-spi-private`. Copy its `authenticateClient` skeleton: obtain the chain via `session.getProvider(X509ClientCertificateLookup.class).getCertificateChain(context.getHttpRequest())`; resolve `client_id` from decoded form params, then query params, then the session attribute `"client_id"`; `ClientAuthUtil.errorResponse` + `context.challenge` for a missing id, `AuthenticationFlowError.CLIENT_NOT_FOUND` / `CLIENT_DISABLED`, `context.attempted()` when no cert is presented. Then, instead of the DN/CA logic (subject-DN, CA-subject-DN, regex options), compare the presented leaf certificate byte-for-byte with the certificate in the client's credential config. Register the factory in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory`.

**Dependent changes.**
- Discovery: `OIDCWellKnownProvider` builds `token_endpoint_auth_methods_supported` (and introspection/revocation lists) from `getClientAuthMethodsSupported()`, which is derived from registered `ClientAuthenticatorFactory` instances — the new factory must expose the OIDC method name (the exact hook is in `ClientAuthenticatorFactory`, not inspected). Auth-method name constants live next to `OIDCLoginProtocol.TLS_CLIENT_AUTH`.
- Security profiles: `services/src/main/resources/keycloak-default-client-profiles.json` mentions `client-x509` in roughly eight places; the new provider id must be tolerated alongside it.

**Easy to miss.**
- `DefaultClientValidationProvider.validateX509Credentials` and `TlsClientAuthCASubjectDNExecutor` both branch on `X509ClientAuthenticator.PROVIDER_ID` and warn/enforce about CA subject DN — the new provider must not be dragged into that CA logic.
- `ClientIdMetadataDocumentExecutor.ALLOWED_ALGORITHMS` lists `PRIVATE_KEY_JWT`, `TLS_CLIENT_AUTH`.
- `DefaultAuthenticationFlows` (server-spi-private) and the admin UI `js/apps/admin-ui/src/clients/credentials/Credentials.tsx` (plus server-info mock JSONs) hard-code `client-x509`.

**Verification.** Follow `tests/base/.../client/AbstractMutualTLSClientTest.java`; also relevant: `OAuth2_1ConfidentialClientTest`, `OIDCClientRegistrationTest`, the FAPI1/FAPI2/FAPICIBA tests and the ClientPolicies tests under `testsuite/integration-arquillian/tests/base`. Cover: same cert accepted; different cert refused; re-issued cert with identical subject DN and key refused.
