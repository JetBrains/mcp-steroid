# Hand-off note: self-signed-certificate client authentication (Keycloak)

## Goal
Add a new client authenticator: the client is authenticated iff the certificate presented at the TLS handshake is byte-for-byte identical to the certificate stored in the client's credential configuration. No trust store / CA chain, no Subject DN matching.

## What to imitate
`services/src/main/java/org/keycloak/authentication/authenticators/client/X509ClientAuthenticator.java` (`PROVIDER_ID = "client-x509"`) is the closest model. It shows the whole shape: get `X509ClientCertificateLookup` from the session, `provider.getCertificateChain(context.getHttpRequest())`, resolve `client_id` from form data → query params → session attribute, `context.setClient`, checks for missing client / disabled client, and the `getProtocolAuthenticatorMethods` list that returns `OIDCLoginProtocol.TLS_CLIENT_AUTH` (line ~262). It extends `AbstractClientAuthenticator`. Its existing logic (subject DN attrs `x509.subjectdn`, `x509.casubjectdn`, regex option, `CertificateValidator`) is exactly what the new authenticator must *not* do.

For the stored certificate, look at how client certificates are kept as client attributes: `services/src/main/java/org/keycloak/services/util/CertificateInfoHelper.java` (`getCertificateFromClient(client, attributePrefix)`; attribute suffixes `certificate`, `private.key`, `public.key`, `kid`) and `JWTClientAuthenticator.ATTR_PREFIX = "jwt.credential"` / `CERTIFICATE_ATTR = "jwt.credential.certificate"`. `KeycloakModelUtils.getCertificate(String)` (server-spi-private) parses a PEM string.

## Changes and their dependencies
1. New authenticator class in the same package, with its own PROVIDER_ID and a new OIDC auth-method constant (constants live in `services/.../protocol/oidc/OIDCLoginProtocol.java`, e.g. `TLS_CLIENT_AUTH = "tls_client_auth"`).
2. Register it in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory` — otherwise it does not exist at runtime.
3. Discovery: `OIDCWellKnownProvider.getClientAuthMethodsSupported()` enumerates `ClientAuthenticator` factories and maps them to protocol auth methods, so the method name appears automatically once (1)+(2) are done and the factory reports it. Dynamic registration resolution goes through `AuthorizeClientUtil.findClientAuthenticatorForOIDCAuthMethod` in `DescriptionConverter`.
4. Client profiles: add the new provider id next to every `"client-x509"` occurrence in `services/src/main/resources/keycloak-default-client-profiles.json` (7 places).

## Easy to miss
- `DefaultClientValidationProvider.validateX509Credentials` warns about `x509.casubjectdn`/regex only for `client-x509`; the new type must not be dragged into it.
- Other places keyed on `client-x509`: `DefaultAuthenticationFlows` (line ~517), admin-ui `clients/credentials/Credentials.tsx` (switches to `X509.tsx` on `client-x509`), `ClientIdMetadataDocumentExecutor`, `TlsClientAuthCASubjectDNExecutor(Factory)` — check whether each should also handle the new type; unknown from this record.

## Verification
Existing suites reference `X509ClientAuthenticator`: `tests/base/.../client/AbstractMutualTLSClientTest.java`, FAPI1/FAPI2/OAuth2_1 tests, `OIDCClientRegistrationTest`, and the client-policy tests under `testsuite/.../client/policies/`. Mirror the mutual-TLS test to cover: same cert accepted; different cert rejected; re-issued cert with identical subject DN and key rejected.
