## Hand-off note: self-signed-certificate client authentication

**Goal** New client authenticator: authenticate a client iff the TLS-presented cert equals (byte-for-byte) the cert stored on the client's credential config; no trust store, no CA chain, no Subject DN matching.

**Model to imitate** `services/.../authentication/authenticators/client/X509ClientAuthenticator.java` (`PROVIDER_ID = "client-x509"`). It extends `AbstractClientAuthenticator` (which implements both `ClientAuthenticator` and `ClientAuthenticatorFactory`), pulls the chain from the `X509ClientCertificateLookup` session provider, resolves `client_id` from form data → query params → session attribute, and fails via `context.failure(...)`/`challenge(...)`. Reuse the lookup + client-resolution part; drop the CA/Subject-DN part (`ATTR_SUBJECT_DN`, `ATTR_CA_SUBJECT_DN`, `CertificateValidator`).

Stored client certs are read via `services/.../services/util/CertificateInfoHelper` (attribute `<prefix>.certificate`, constant `X509CERTIFICATE`); `JWTClientAuthenticator` uses prefix `jwt.credential` (admin UI `clients/keys/Keys.tsx` hard-codes the same). `KeycloakModelUtils.getCertificate(String)` parses a PEM.

**Dependent changes**
1. Register the class in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory`.
2. Discovery: `OIDCWellKnownProvider.getClientAuthMethodsSupported()` simply maps every `ClientAuthenticatorFactory`, so the new factory's protocol-auth-methods must return a new method name (X509 returns `OIDCLoginProtocol.TLS_CLIENT_AUTH`, defined in `OIDCLoginProtocol`, line ~129). Dynamic registration then resolves it through `AuthorizeClientUtil.findClientAuthenticatorForOIDCAuthMethod` in `clientregistration/oidc/DescriptionConverter`.
3. Add the new provider id next to each `"client-x509"` occurrence in `services/src/main/resources/keycloak-default-client-profiles.json` (7 places, `secure-client-authenticator` executor) so FAPI/OAuth2.1 profiles accept it.
4. Likely add an ALTERNATIVE execution in `DefaultAuthenticationFlows.clientAuthFlow` (client-x509 has priority 40; note `federated-jwt`/`attestation-based` are feature-gated). Whether existing realms need a migrator is unknown — no recent `MigrateTo*` touches this flow.

**Easy to miss** `DefaultClientValidationProvider.validateX509Credentials` and `TlsClientAuthCASubjectDNExecutor` key off `X509ClientAuthenticator.PROVIDER_ID` — decide deliberately whether the new type is in scope. Admin UI `clients/credentials/Credentials.tsx` renders `<X509 />` only for `client-x509`.

**Verification** Extend `tests/base/.../client/AbstractMutualTLSClientTest` (run by `MutualTLSClientTest` / `MutualTLSClientDedicatedStoreTest`); `test-framework/core/.../https/ManagedCertificates` generates the self-signed client cert and stores. Cover: matching cert succeeds; a re-issued cert with identical subject DN and key fails.
