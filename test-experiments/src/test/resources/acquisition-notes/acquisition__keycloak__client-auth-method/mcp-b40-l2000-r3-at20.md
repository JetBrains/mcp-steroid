# Hand-off note: self-signed-certificate client authenticator

## What to imitate

`services/src/main/java/org/keycloak/authentication/authenticators/client/X509ClientAuthenticator.java` (`PROVIDER_ID = "client-x509"`) is the closest model: it extends `AbstractClientAuthenticator`, obtains the peer chain via `session.getProvider(X509ClientCertificateLookup.class).getCertificateChain(httpRequest)`, resolves `client_id` from form data → query params → session attribute, then fails with `CLIENT_NOT_FOUND`/`CLIENT_DISABLED`, calls `context.attempted()` when no cert is present, and validates subject DN / CA subject DN from client attributes (`x509.subjectdn`, `x509.casubjectdn`, `x509.allow.regex.pattern.comparison`) using `CertificateValidator`. Reuse the client_id/enabled/attempted skeleton; drop the DN + trust-store parts and instead compare the presented leaf certificate byte-for-byte with the certificate already stored on the client. The stored certificate is reached through `services/src/main/java/org/keycloak/services/util/CertificateInfoHelper.java` (also used by `ClientAttributeCertificateResource`, `ClientPublicKeyLoader`, `DescriptionConverter`); note `JWTClientAuthenticator` stores its cert under attribute prefix `jwt.credential` — confirm which prefix your authenticator should read.

`AttestationBasedClientAuthenticator` is the most recent example of adding an authenticator; its footprint shows the touch points.

## Changes and their dependencies

1. New authenticator class + registration line in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory`.
2. New auth-method constant next to `TLS_CLIENT_AUTH` in `protocol/oidc/OIDCLoginProtocol.java`, returned from your factory's `getProtocolAuthenticatorMethods(OIDCLoginProtocol.LOGIN_PROTOCOL)`. Discovery (`OIDCWellKnownProvider.getClientAuthMethodsSupported`) and dynamic-registration lookup (`AuthorizeClientUtil.findClientAuthenticatorForOIDCAuthMethod`, used by `DescriptionConverter`) are both derived from that, so no further wiring is needed there.
3. Add the provider id to every `secure-client-authenticator` executor's `allowed-client-authenticators` list in `services/src/main/resources/keycloak-default-client-profiles.json` that currently lists `client-x509` (fapi-1-baseline/advanced, fapi-2 variants, fapi-2-dpop variants, oauth-2-1-for-confidential-client).
4. Decide whether to add an ALTERNATIVE execution in `DefaultAuthenticationFlows.clientAuthFlow` (existing priorities: 5 attestation, 10/20/30, 40 client-x509); this changes built-in realm flows.

## Easy to miss

- `DefaultClientValidationProvider` and `TlsClientAuthCASubjectDNExecutor` reference `X509ClientAuthenticator` and may enforce DN attributes — check they don't reject the new type.
- Admin UI `js/apps/admin-ui/src/clients/credentials/Credentials.tsx` switches UI per authenticator id (`client-x509` → `<X509 />`); the new id will show nothing unless added.
- Assertion-based tests will break: `tests/.../admin/authentication/ProvidersTest` (exact provider list), `InitialFlowsTest` (exact clients-flow executions), and discovery tests using `getTokenEndpointAuthMethodsSupported`.

## Verification

Model tests on `tests/base/src/test/java/org/keycloak/tests/client/AbstractMutualTLSClientTest.java` (+ `MutualTLSClientTest`, `MutualTLSClientDedicatedStoreTest`): realm config via `ClientBuilder.authenticatorType(...)`, real TLS client through `ManagedCertificates`, asserting 200/token vs 401/no-token. Add cases: matching stored cert succeeds; re-issued cert with same subject DN and same key fails.
