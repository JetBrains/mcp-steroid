# Hand-off note: self-signed-certificate client authentication (`tls_client_auth`-style, cert-equality based)

## Goal
Add a new client authenticator that authenticates a client iff the certificate presented in the TLS handshake is byte-for-byte equal to the certificate already stored on the client's credential configuration. No trust store, no CA chain, no subject-DN matching. A re-issued cert with the same subject and key must be rejected.

## What to imitate
`services/src/main/java/org/keycloak/authentication/authenticators/client/X509ClientAuthenticator.java` (`PROVIDER_ID = "client-x509"`) is the closest model. Reuse its shape for:
- extending `AbstractClientAuthenticator` (same package);
- obtaining the presented chain via `X509ClientCertificateLookup` SPI (`context.getSession().getProvider(...)`, `provider.getCertificateChain(context.getHttpRequest())`);
- resolving `client_id` from form data, then query params, then session attribute; `ClientAuthUtil.errorResponse(...)` + `context.challenge(...)` when missing; `AuthenticationFlowError.CLIENT_NOT_FOUND` / `CLIENT_DISABLED`; `context.getEvent().client(...)`, `context.setClient(...)`; `context.attempted()` on `GeneralSecurityException`.
- Drop everything DN/CA related (`ATTR_SUBJECT_DN`, `ATTR_CA_SUBJECT_DN`, regex comparison, `CertificateValidator`, custom OIDs).

For reading the certificate stored on the client, look at `services/src/main/java/org/keycloak/services/util/CertificateInfoHelper.java` and how `JWTClientAuthenticator` uses it (this was not inspected in detail — verify).

Two recent additions show the exact file set a new authenticator touches: commit `22e018c` (`AttestationBasedClientAuthenticator`) and `57242d2` (`FederatedJWTClientAuthenticator`).

## Changes and their dependencies
1. New authenticator class in `.../authenticators/client/`, with its own `PROVIDER_ID`.
2. Register it in `services/src/main/resources/META-INF/services/org.keycloak.authentication.ClientAuthenticatorFactory` (currently lists 6 authenticators).
3. Add the new auth-method name constant next to `TLS_CLIENT_AUTH` in `services/.../protocol/oidc/OIDCLoginProtocol.java:129`. Discovery is automatic: `OIDCWellKnownProvider.getClientAuthMethodsSupported()` iterates factories and calls `getProtocolAuthenticatorMethods(OIDCLoginProtocol.LOGIN_PROTOCOL)` — so returning the new name from your factory (as `X509ClientAuthenticator` does at line 262) puts it into token/introspection/revocation auth methods.
4. Client policies: `SecureClientAuthenticatorExecutor` and `services/src/main/resources/keycloak-default-client-profiles.json` reference `client-x509`; the new provider id must be allowed there too. `ClientIdMetadataDocumentExecutor` also whitelists `TLS_CLIENT_AUTH` — check whether it needs the new value.

## Easy to miss
- `DefaultAuthenticationFlows` (server-spi-private) references `client-x509`; check whether the built-in client-auth flow needs an execution for the new provider.
- Admin UI (`js/apps/admin-ui/.../Credentials.tsx`) and server-info mocks/tests reference `client-x509`.
- `ProvidersTest` / `InitialFlowsTest` under `tests/base` enumerate client authenticators and will fail until updated.

## Verification
Mirror the FAPI/registration tests that use `TLS_CLIENT_AUTH` (`FAPI1Test`, `FAPI2Test`, `AbstractFAPI2Test`, `OIDCClientRegistrationTest`, `ClientPoliciesExecutorTest`): dynamic registration with the new method, plus positive (identical cert) and negative (re-issued same-subject/same-key cert) token-endpoint tests.
