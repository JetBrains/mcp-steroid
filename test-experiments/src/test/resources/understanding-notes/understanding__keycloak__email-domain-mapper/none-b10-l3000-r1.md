**Where the work goes** (verified): `services/src/main/java/org/keycloak/protocol/oidc/mappers/`, package `org.keycloak.protocol.oidc.mappers`. Neighbours: `UserPropertyMapper`, `FullNameMapper`, `HardcodedClaim`, `SubMapper`, `SessionStateMapper`.

**The model to imitate: `FullNameMapper`** — not `UserPropertyMapper`. Both implement `AbstractOIDCProtocolMapper` + `OIDCAccessTokenMapper, OIDCIDTokenMapper, UserInfoTokenMapper, TokenIntrospectionTokenMapper` (all four exist here; the introspection one is confirmed). The difference: `UserPropertyMapper` calls `OIDCAttributeMapperHelper.addAttributeConfig(...)`, which exposes a user-editable *claim name* field. You need a **fixed** claim name `email_domain`, which is `FullNameMapper`'s situation ("name"/"given_name"), so copy its use of `OIDCAttributeMapperHelper.addIncludeInTokensConfig(configProperties, YourClass.class)` — that alone contributes the four admin switches (ID token / access token / userinfo / introspection). Read `FullNameMapper` fully before writing anything; it is short and is the whole template, including its `static ProtocolMapperModel create(name, accessToken, idToken, introspectionEndpoint)` helper used by the builtins registration.

Boilerplate that must be present: `PROVIDER_ID = "oidc-email-domain-mapper"`, `getId()` returning it, `getDisplayCategory()` returning the inherited `TOKEN_MAPPER_CATEGORY` constant, `getDisplayType()`, `getHelpText()`, and `getConfigProperties()` returning the static list (easy to forget — the excerpt I saw of `UserPropertyMapper` elided it, but it is required for the admin console).

**The logic.** Override the *5-arg* `setClaim(IDToken token, ProtocolMapperModel mappingModel, UserSessionModel userSession, KeycloakSession session, ClientSessionContext clientSessionCtx)` — there is also a deprecated 3-arg overload; check which one `AbstractOIDCProtocolMapper` dispatches to. The base class's `transformIDToken/AccessToken/UserInfoToken/IntrospectionToken` already consult the include-in-X config and only then call `setClaim`, so honouring the switches is free — do **not** re-implement the transform methods. The spec says the e-mail of *the token being issued*, so read `token.getEmail()` (`org.keycloak.representations.IDToken` — I believe it has `getEmail()`; verify), not `userSession.getUser().getEmail()`. Guard: null/blank e-mail, no `@`, or empty part after the last `@` → return without touching the token. Otherwise `token.getOtherClaims().put("email_domain", domain)`. Note `OIDCAttributeMapperHelper.mapClaim(...)` derives the claim name from config, so it is probably the wrong helper here.
