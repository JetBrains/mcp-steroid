Target: Keycloak. Everything lives in the `services` module (`./mvnw -q -DskipTests compile -pl services` to compile-check; don't build the reactor).

**Where to put the class**
`services/src/main/java/org/keycloak/protocol/oidc/mappers/` — all OIDC token mappers sit here. Imitate the smallest existing ones: `HardcodedClaim.java`, `AudienceProtocolMapper.java`, `SHA256PairwiseSubMapper.java`, `UserPropertyMapper.java` (that last one is what produces the builtin `email` claim). Extend `AbstractOIDCProtocolMapper` and implement all four marker interfaces `OIDCIDTokenMapper, OIDCAccessTokenMapper, UserInfoTokenMapper, TokenIntrospectionTokenMapper` — that is exactly what makes the four admin switches meaningful.

**How the flow works.** `AbstractOIDCProtocolMapper` implements `transformIDToken/transformAccessToken/transformUserInfoToken/transformIntrospectionToken`; each one first checks `OIDCAttributeMapperHelper.includeInIDToken/includeInAccessToken/includeInUserInfo/includeInIntrospection(mappingModel)` and only then calls the protected hook `setClaim(IDToken token, ProtocolMapperModel mappingModel, UserSessionModel userSession, KeycloakSession keycloakSession, ClientSessionContext clientSessionCtx)`. So you override *only* `setClaim` and the admin switches are honoured for free — do not re-implement the transform methods. Note the userinfo/introspection paths hand an `AccessToken` to that `IDToken` parameter, i.e. `AccessToken` is an `IDToken` subclass, so `token.getEmail()` works in every path (one exploration report claimed they are unrelated classes — I believe that is wrong, but verify the declaration of `AccessToken` before relying on it).

**setClaim body**: take `token.getEmail()`; if null/blank, or `indexOf('@') < 0`, return without touching the token; otherwise put the substring after the last/first `@` under the claim name. Because the claim name is fixed by the spec, the least risky route is a `public static final String CLAIM_NAME = "email_domain"` written straight into `token.getOtherClaims()`, rather than going through `OIDCAttributeMapperHelper.mapClaim(...)` which resolves the configurable `claim.name` (`OIDCAttributeMapperHelper.TOKEN_CLAIM_NAME`) and would emit nothing if an admin left it empty. If you do want configurability, default it to `email_domain` in both `getConfigProperties()` and `create()`.

**Config/admin console**: `getConfigProperties()` should be a `new ArrayList<ProviderConfigProperty>()` passed to `OIDCAttributeMapperHelper.addIncludeInTokensConfig(list, YourMapper.class)` — it reflects over the interfaces you implement to add the id/access/userinfo/introspection checkboxes. Do *not* call `addAttributeConfig`/`addTokenClaimNameConfigProperty` unless you want the claim-name and jsonType fields. `getDisplayCategory()` must return the shared constant on `AbstractOIDCProtocolMapper` (`TOKEN_MAPPER_CATEGORY`, "Token mapper") — that is the "usual token-mapper category". `getId()` returns `"oidc-email-domain-mapper"`; keep it in a `public static final String PROVIDER_ID`. Add `getDisplayType()` and `getHelpText()`.

**Three registration steps, easy to forget:**
1. Add the FQCN as a new line in `services/src/main/resources/META-INF/services/org.keycloak.protocol.ProtocolMapper`. Without this, `session.getProvider(ProtocolMapper.class, "oidc-email-domain-mapper")` returns null and the type never reaches the admin console's mapper-type list (`ServerInfoAdminResource` → `protocolMapperTypes`).
2. Make it a *builtin*: `services/src/main/java/org/keycloak/protocol/oidc/OIDCLoginProtocolFactory.java` keeps a static `builtins` map (`Map<String, ProtocolMapperModel>`) populated in a static initializer via entries like the `USERNAME`/`EMAIL`/full-name ones, and returns it from `getBuiltinMappers()`. That map is what the server "ships with" and what is surfaced as `builtinProtocolMappers` in server-info / the predefined-mapper dialog. Add one entry there, using a `public static ProtocolMapperModel create(String name, boolean idToken, boolean accessToken, boolean userInfo, boolean introspection)` helper on your mapper that sets name, `setProtocolMapper(PROVIDER_ID)`, `setProtocol(OIDCLoginProtocol.LOGIN_PROTOCOL)` and the four `INCLUDE_IN_*` config flags ("true"/"false" strings). Mirror the idiom of a neighbouring entry exactly.
3. Only if a test demands the claim actually appear in tokens of a fresh realm would you also attach it to a default client scope in the same factory's `createDefaultClientScopes`-style method (the `email` scope is the natural host). I'd avoid that unless required: it changes the tokens every realm issues and can break unrelated testsuite assertions. Presence in `builtins` is the normal reading of "administrator finds it among the mappers the server ships with".
