Repo is Keycloak main (version 999.0.0-SNAPSHOT). My exploration budget was consumed almost immediately, so treat everything below as *verified file existence + my prior knowledge of this codebase*, and re-check the details I flag.

**Where the work goes.** `services/src/main/java/org/keycloak/protocol/oidc/mappers/`. Confirmed present there: `AbstractOIDCProtocolMapper`, `OIDCAttributeMapperHelper` (~25 KB, the config/claim-writing helper), and the marker interfaces `OIDCIDTokenMapper`, `OIDCAccessTokenMapper`, `UserInfoTokenMapper`, `TokenIntrospectionTokenMapper`, `OIDCAccessTokenResponseMapper`. Also `HardcodedClaim`, `UserAttributeMapper`, `UserPropertyMapper`, `UserSessionNoteMapper`, `ClaimsParameterTokenMapper`, `FullNameMapper`, `AddressMapper`, `AudienceProtocolMapper`.

**Imitate, don't invent.** The closest templates are `HardcodedClaim` (config-property boilerplate) and `FullNameMapper`/`ClaimsParameterTokenMapper` (compute a claim rather than copy an attribute). Pattern: extend `AbstractOIDCProtocolMapper`, implement the four interfaces above (ID, access, userinfo, introspection), declare a static `List<ProviderConfigProperty>`, and override the protected `setClaim(IDToken token, ProtocolMapperModel model, UserSessionModel userSession, KeycloakSession session, ClientSessionContext ctx)` hook. The `transform*Token` methods in the base class are final and already consult `OIDCAttributeMapperHelper.includeInIDToken/AccessToken/UserInfo/Introspection`, so the four admin switches come for free **provided** you build the config list with `OIDCAttributeMapperHelper.addIncludeInTokensConfig(configProperties, YourMapper.class)` — that helper reflects over the implemented interfaces to decide which checkboxes to emit. `getDisplayCategory()` must return the same token-mapper-category constant `HardcodedClaim` returns (defined on `AbstractOIDCProtocolMapper`/`ProtocolMapperUtils`). `getId()` → `"oidc-email-domain-mapper"`.

**The claim.** Read the e-mail off the token (`IDToken.getEmail()`; `AccessToken extends IDToken`), split on the last/first `@`, and only `token.getOtherClaims().put("email_domain", domain)` when a non-empty part exists. Gotcha I could not verify: the `email` claim is itself produced by the builtin *email* property mapper, so ordering matters — check `ProtocolMapper.getPriority()` and how `UserPropertyMapper` lands `email` (field vs `otherClaims`). Be defensive: consider both `getEmail()` and `getOtherClaims().get("email")`, or override `getPriority()` to run late. Verify this before assuming.

**Two registrations that are easy to forget.**
1. SPI: add the FQCN to `services/src/main/resources/META-INF/services/org.keycloak.protocol.ProtocolMapper` (confirm the exact file name in that directory) — without it the provider id is not resolvable at runtime.
2. "Ships out of the box": `services/.../protocol/oidc/OIDCLoginProtocolFactory.java` — `init()` fills the `builtins` map (exposed via `getBuiltinMappers()`, surfaced to the admin console through the server-info admin resource). Add an entry there, built by a static `create(...)`/`createClaimMapper(...)` factory on your mapper returning a `ProtocolMapperModel` with protocol `OIDCLoginProtocol.LOGIN_PROTOCOL`. Note the distinct `defaultBuiltins` list (mappers auto-attached to default client scopes/new clients) — the task only asks that the mapper be *available* predefined, so prefer `builtins` only and avoid changing default client scopes, which would perturb many fixtures.

**Don't change** existing mapper ids, claim names, `OIDCAttributeMapperHelper` semantics, or default client scopes.
