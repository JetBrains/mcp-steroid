**Repo = Keycloak (multi-module Maven).** Everything you need is in the `services` module: `services/src/main/java/org/keycloak/protocol/oidc/mappers/` (~38 mapper classes) plus the OIDC protocol factory one package up. Build/compile only that module: `JAVA_HOME=/usr/lib/jvm/temurin-21-jdk-... ./mvnw -pl services compile`.

**Imitate an existing mapper.** `HardcodedClaim.java` in that package is the closest short template (verified: ~124 lines). Its shape: `public class X extends AbstractOIDCProtocolMapper implements OIDCAccessTokenMapper, OIDCIDTokenMapper, UserInfoTokenMapper, TokenIntrospectionTokenMapper` (drop `OIDCAccessTokenResponseMapper` unless you want the token-response too — not requested), a `private static final List<ProviderConfigProperty> configProperties = new ArrayList<>();` filled in a `static {}` block, then `getId()`, `getDisplayType()`, `getDisplayCategory()` (return the inherited `TOKEN_MAPPER_CATEGORY` constant — that is the "usual token-mapper category" the task means), `getHelpText()`, `getConfigProperties()`, and an override of `setClaim(...)`. `UserSessionNoteMapper.java` is the second-best model (it computes a value at runtime instead of hardcoding it).

**Why one `setClaim` override is enough.** `AbstractOIDCProtocolMapper` (same package) implements `transformIDToken`, `transformAccessToken`, `transformUserInfoToken`, `transformIntrospectionToken` and `transformAccessTokenResponse`; each first consults the corresponding `OIDCAttributeMapperHelper.includeInIDToken/includeInAccessToken/includeInUserInfo/includeInIntrospection(mappingModel)` switch and only then delegates to `setClaim(IDToken token, ProtocolMapperModel, UserSessionModel, KeycloakSession, ClientSessionContext)`. `AccessToken extends IDToken`, so overriding the `IDToken` variant covers all four destinations and you get the four admin switches for free — provided `getConfigProperties()` includes them via `OIDCAttributeMapperHelper.addIncludeInTokensConfig(configProperties, YourMapper.class)`. Check the exact `setClaim` signature in `AbstractOIDCProtocolMapper` (around lines 143-174) — there is a deprecated narrower overload; override the widest one.

**The logic.** Read the e-mail off the token being issued: `token.getEmail()` (field on `IDToken`, core module). If null/blank, or `indexOf('@') < 0`, return without touching the token. Otherwise put the substring after the last/first `@` into `token.getOtherClaims().put("email_domain", domain)`. I found no pre-existing `email_domain` code anywhere (unverified — my grep budget ran out, so grep it once yourself). Using `OIDCAttributeMapperHelper.mapClaim(token, mappingModel, value)` instead is the idiomatic route but it depends on a `claim.name`/`jsonType` entry in the mapper config; since the claim name is fixed by the spec, writing `otherClaims` directly is safer and cannot silently no-op when a builtin model omits that config.

**Two registrations — the easy-to-forget part.**
1. SPI/ServiceLoader: append the fully-qualified class name to `services/src/main/resources/META-INF/services/org.keycloak.protocol.ProtocolMapper` (one FQCN per line). `ProtocolMapper` is its own provider factory, so `getId()` returning `"oidc-email-domain-mapper"` is what makes it resolvable at runtime and listed as an available mapper type in server info / admin console. Missing this line is the classic failure.
2. "Ships with the server": `services/src/main/java/org/keycloak/protocol/oidc/OIDCLoginProtocolFactory.java` holds a static `builtins` map (`Map<String, ProtocolMapperModel>`, plus a `defaultBuiltins` list) populated in a static/`init`-time block using per-mapper static factories like `UserPropertyMapper.createClaimMapper(...)` / `HardcodedClaim.create(...)`, and exposed through `getBuiltinMappers()` (surfaced to the admin console as the builtin-protocol-mapper list). Give your class a static `create(...)`/factory returning a `ProtocolMapperModel` (protocol `OIDCLoginProtocol.LOGIN_PROTOCOL`, protocolMapper = your id, config with the four include-in flags true) and register it in that block. I did not get to confirm the exact method names in that file — read it first. Note the distinction: `builtins` = offered/shipped; `defaultBuiltins` and `createDefaultClientScopes(...)` (same file, called from `RealmManager` when a realm is created) = actually pre-attached to a new realm's default client scopes. The task wording ("a freshly created realm's administrator must find it among the mappers the server ships with, without creating it by hand") points at `builtins`; only add it to a default client scope if you decide the stronger reading is intended, and be aware that changes token content for every new realm and can break token-assertion tests.

**Risks / do-not-touch.** Don't edit existing mappers, don't reorder or remove lines in the services file, don't change existing default client scopes. Some testsuite classes and JSON fixtures enumerate available mapper ids or builtin-mapper counts (e.g. server-info/admin-console assertions, migration fixtures) — I could not verify which; if a test fails with an off-by-one on a mapper list, that is the second place to update, not a bug in your mapper.

**Verification.** Integration tests live under `testsuite/integration-arquillian/tests/base/src/test/java/org/keycloak/testsuite/oidc/` — from memory `OIDCProtocolMappersTest` (and `ProtocolMappersTest` under `admin/`) is the right pattern: build a `ProtocolMapperRepresentation` (protocol `openid-connect`, protocolMapper = provider id, config with `id.token.claim`/`access.token.claim`/`userinfo.token.claim`/`introspection.token.claim` = "true"), attach it to a client, fetch a token and assert `token.getOtherClaims().get("email_domain")`. Verify those class names exist before relying on them. Cheapest local check is compiling `services` and a small unit test asserting your `setClaim` behaviour for: normal e-mail, null e-mail, e-mail without `@`.
