Repo is Keycloak. Everything you need is in the `services` module.

**Imitate an existing mapper.** New class in `services/src/main/java/org/keycloak/protocol/oidc/mappers/` (e.g. `EmailDomainMapper`), extending `AbstractOIDCProtocolMapper` and implementing `OIDCIDTokenMapper, OIDCAccessTokenMapper, UserInfoTokenMapper, TokenIntrospectionTokenMapper`. Look at `HardcodedClaim`, `SubMapper`, `SessionStateMapper`, `AudienceProtocolMapper` as templates (I ran out of budget before reading them — read one first). The base class's `transformIDToken/transformAccessToken/transformUserInfoToken/transformIntrospectionToken` already gate on the admin switches (via `OIDCAttributeMapperHelper.includeInIDToken(...)` etc.) *and* on which of those four interfaces you implement — implement all four or the corresponding switch silently does nothing. Do the work in the `setClaim(IDToken token, ...)` override (AccessToken extends IDToken, so one override covers all paths); read `token.getEmail()`, split on `@`, and simply return without touching the token when email is null/blank or has no `@`.

Config: a `static final List<ProviderConfigProperty>` built with `OIDCAttributeMapperHelper.addIncludeInTokensConfig(list, EmailDomainMapper.class)` (verify that helper also adds the introspection switch in this version; if not, add `INCLUDE_IN_INTROSPECTION` yourself). `getDisplayCategory()` must return the token-mapper category constant (`AbstractOIDCProtocolMapper.TOKEN_MAPPER_CATEGORY` / `ProtocolMapperUtils.TOKEN_MAPPER_CATEGORY` — check which exists). `getId()` → `"oidc-email-domain-mapper"`.

**Two registration steps, both required:**
1. Add the FQCN to `services/src/main/resources/META-INF/services/org.keycloak.protocol.ProtocolMapper` (single file; gives runtime resolution by provider id).
2. `services/.../protocol/oidc/OIDCLoginProtocolFactory.java`: add a name constant (~L90-118), a static `create(...)` returning a configured `ProtocolMapperModel`, and `builtins.put(NAME, model)` inside `initBuiltIns()` (~L192-291, called from `init()` L177). `getBuiltinMappers()` (L186) is what new realms/admin console see — this is the "ships out of the box" requirement.

**Careful:** builtins are keyed by *display name*, not provider id. Do NOT also wire it into a default client scope (`initBuiltIns` L302-395) — that changes every new realm and will break default-scope assertions. Ordering risk I could not verify: your claim depends on the `email` claim already being set by the email property mapper; mappers run sorted by `getPriority()`, so you may need a priority above the default. Don't touch existing mappers.

Verify by grepping the testsuite for `oidc-full-name-mapper` to find tests enumerating built-in/provider lists and copy that pattern.
