**Verified in this tree**

OIDC token mappers live in `services/src/main/java/org/keycloak/protocol/oidc/mappers/` (~37 classes). Base class `AbstractOIDCProtocolMapper` implements `ProtocolMapper`; the four opt-in interfaces all exist there: `OIDCIDTokenMapper`, `OIDCAccessTokenMapper`, `UserInfoTokenMapper`, `TokenIntrospectionTokenMapper`. The base class provides `transformIDToken/transformAccessToken/transformUserInfoToken/transformIntrospectionToken/transformAccessTokenResponse(...)` (each taking `ProtocolMapperModel, KeycloakSession, UserSessionModel, ClientSessionContext`) and the protected hooks a subclass overrides: `setClaim(IDToken token, ProtocolMapperModel, UserSessionModel, KeycloakSession, ClientSessionContext)` (the non-deprecated 5-arg form — use this one; the 3-arg one is `@Deprecated`) and a `setClaim(AccessTokenResponse ...)` variant you do not need. `OIDCAttributeMapperHelper` holds `INCLUDE_IN_ACCESS_TOKEN`, `INCLUDE_IN_ID_TOKEN`, `INCLUDE_IN_USERINFO`, `INCLUDE_IN_INTROSPECTION` plus `includeInIDToken/includeInAccessToken/includeInUserInfo/includeInIntrospection(mappingModel)`. Those checks live inside the base class's `transform*` methods, so **the admin switches come for free** if you (a) implement all four interfaces and (b) only override `setClaim`. Never re-implement the include logic yourself.

**Plan (my recommendation)**

1. New class `services/.../protocol/oidc/mappers/EmailDomainMapper` (name is yours), `extends AbstractOIDCProtocolMapper implements OIDCIDTokenMapper, OIDCAccessTokenMapper, UserInfoTokenMapper, TokenIntrospectionTokenMapper`. Copy the *whole* skeleton of `HardcodedClaim` (or `SHA256PairwiseSubMapper` if it fits better) verbatim: static `List<ProviderConfigProperty> configProperties`, a static initializer calling `OIDCAttributeMapperHelper.addIncludeInTokensConfig(configProperties, YourClass.class)` (do **not** add token-claim-name / json-type config — the claim name is fixed), `getConfigProperties()`, `getId()` returning `"oidc-email-domain-mapper"`, `getDisplayType()`, `getDisplayCategory()` returning the same `TOKEN_MAPPER_CATEGORY` constant the neighbours use, `getHelpText()`.
2. In `setClaim`, read the e-mail from the token itself (`IDToken.getEmail()`; `AccessToken extends IDToken`). If null/blank or `indexOf('@') < 0`, return without touching the token. Otherwise put the substring after the **last** `@` (or after the first — pick one; `substringAfterLast` is the safer reading of "the part after @") under literal claim name `email_domain`, using the same mechanism the neighbours use (`OIDCAttributeMapperHelper.mapClaim(token, mappingModel, value)` writes to the configured claim name, so for a fixed name you may instead need `token.getOtherClaims().put("email_domain", domain)` — check what `mapClaim` does before choosing).
3. **Easy to forget #1:** register the class in the SPI service file `services/src/main/resources/META-INF/services/org.keycloak.protocol.ProtocolMapper`. Without this line the provider id is not resolvable at runtime at all. Append; don't reorder existing lines.
4. **Easy to forget #2 — the "ships with it" requirement:** `services/src/main/java/org/keycloak/protocol/oidc/OIDCLoginProtocolFactory.java` keeps a `Map<String, ProtocolMapperModel> builtins` and a `List<ProtocolMapperModel> defaultBuiltins`, populated in a static initializer (possibly in `init(Config.Scope)` — check), and exposes `getBuiltinMappers()` (from `LoginProtocolFactory`), which is what the admin REST/server-info "builtin protocol mappers" listing serves. Add a `public static ProtocolMapperModel create(String name, boolean accessToken, boolean idToken, boolean introspection...)` helper on your mapper (imitate the `create`/`createClaimMapper` helpers on `HardcodedClaim`/`UserPropertyMapper`) and put one entry into `builtins`, matching the surrounding idiom exactly (note whether the map key is the display name or the provider id). Be deliberate about `defaultBuiltins`: that list is what gets attached to newly created clients/default client scopes, and adding to it changes every new realm's default token contents — likely to break export/import, migration-JSON and admin assertions. Prefer `builtins` only unless the requirement clearly demands otherwise.

**Ordering gotcha (unverified, but worth checking)**: mappers run sorted by `ProtocolMapper#getPriority()`. If the built-in e-mail mapper runs *after* yours, `token.getEmail()` will still be null and the claim silently disappears — especially for access tokens and lightweight access tokens. Look at `ProtocolMapperUtils`' `PRIORITY_*` constants and consider overriding `getPriority()` so your mapper runs late. Consider whether falling back to `userSession.getUser().getEmail()` is acceptable — the spec says "the e-mail carried by the token", so a fallback may be wrong; test-driven decision.

**Verification.** Don't run the reactor. `JAVA_HOME=/usr/lib/jvm/temurin-21-jdk-<resolved> ./mvnw -pl services compile` (module artifact `keycloak-services`) is the cheap check. The end-to-end pattern to imitate is the arquillian suite under `testsuite/integration-arquillian/tests/base/src/test/java/org/keycloak/testsuite/oidc/` (look for `OIDCProtocolMappersTest`): it adds a mapper to a client, logs in, and asserts claims in ID token / access token / userinfo / introspection. That suite needs a running server, so it is slow; a small unit test instantiating the mapper and calling `transformIDToken` with a hand-built `IDToken` + `ProtocolMapperModel` covers the "@"-less and no-e-mail cases much faster.

**Do not change**: existing mapper ids, display types, the existing lines of the SPI file, or the contents of `defaultBuiltins`/default client scopes beyond what is required. Also grep for tests asserting the *size* of the builtin-mapper set or server-info listings — I never got to check for those, and they are the most likely collateral breakage.
