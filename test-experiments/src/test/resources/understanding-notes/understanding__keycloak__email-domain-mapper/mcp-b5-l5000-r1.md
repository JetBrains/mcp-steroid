## What I verified vs. guessed

I burned my interaction budget on one deep read of the mapper layer; the registration/test/email questions I could not confirm. Everything under "Verified" I saw; everything under "Verify yourself" is my best inference from Keycloak's design — check it with the indexing tools before trusting it.

## Verified

Mappers live in module **`services`**, package `org.keycloak.protocol.oidc.mappers`
(`services/src/main/java/org/keycloak/protocol/oidc/mappers/`, ~38 classes).

**Imitate `HardcodedClaim`** — it is the closest template (computes a value in code, no attribute lookup). Its shape:

- `class X extends AbstractOIDCProtocolMapper implements OIDCAccessTokenMapper, OIDCIDTokenMapper, UserInfoTokenMapper, OIDCAccessTokenResponseMapper, TokenIntrospectionTokenMapper` — for this task you need all but `OIDCAccessTokenResponseMapper` (ID token, access token, userinfo, introspection). Those four marker interfaces are what makes the mapper *offered* for each destination.
- `public static final String PROVIDER_ID = "oidc-email-domain-mapper";` returned from `getId()`.
- static `List<ProviderConfigProperty> configProperties`, filled in a static block with `OIDCAttributeMapperHelper.addIncludeInTokensConfig(configProperties, X.class)` (this one call adds all four admin switches). `addTokenClaimNameConfig` / `addJsonTypeConfig` exist too but you probably do **not** want them: the claim name is fixed to `email_domain`.
- `getDisplayCategory()` returns the inherited constant `TOKEN_MAPPER_CATEGORY` ("Token mapper"); also implement `getDisplayType()`, `getHelpText()`, `getConfigProperties()`.

`AbstractOIDCProtocolMapper` already implements `transformIDToken`, `transformAccessToken`, `transformUserInfoToken`, `transformIntrospectionToken` and each one checks `OIDCAttributeMapperHelper.includeInIDToken / includeInAccessToken (or includeInLightweightAccessToken) / includeInUserInfo / includeInIntrospection` before calling `setClaim`. **So you get the admin switches for free — do not override the transform* methods.** Override only:

`protected void setClaim(IDToken token, ProtocolMapperModel mappingModel, UserSessionModel userSession, KeycloakSession keycloakSession, ClientSessionContext clientSessionCtx)`

(the 5-arg form; the 4-arg overload is deprecated and only delegated to for back-compat). Write the value with `token.getOtherClaims().put("email_domain", domain)` (a `OIDCAttributeMapperHelper.mapClaim(token, mappingModel, value)` call would use the *configured* claim name, which you aren't exposing). Return early — adding nothing — when the email is null/blank or has no `@`; take the substring after the **last** `@`.

## Verify yourself (my inferences)

**Getting the email.** I could not confirm whether `IDToken.getEmail()` still exists as a typed field or whether the built-in email claim only lands in `otherClaims`. Check `org.keycloak.representations.IDToken` and follow `OIDCAttributeMapperHelper.mapClaim`. Robust implementation: try `token.getEmail()` if the accessor exists, else/also `token.getOtherClaims().get("email")` (as String). A second risk is **ordering**: your mapper may run before the built-in email mapper, so the token's email is not set yet. `ProtocolMapper.getPriority()` governs order (check who overrides it and where `TokenManager` sorts the mapper stream). If ordering is not guaranteed, either give your mapper a higher priority than the email mapper, or fall back to `userSession.getUser().getEmail()`. Decide deliberately — the task says "the e-mail carried by the token", so token first, user only as fallback.

**Two registration places, both required.**
1. Runtime resolution by provider id: add the fully-qualified class name to the SPI file `services/src/main/resources/META-INF/services/org.keycloak.protocol.ProtocolMapper` (confirm the exact path/filename; check whether another copy exists elsewhere, e.g. a test or quarkus module).
2. "Ships with the server / present in a fresh realm": `services/.../protocol/oidc/OIDCLoginProtocolFactory.java`. It keeps a `builtins` map (and, I believe, a `defaultBuiltins` list) populated in a static block, typically `ProtocolMapperModel model = SomeMapper.createXxxMapper(...); builtins.put(model.getName(), model);`. So add a `public static ProtocolMapperModel create(...)` factory on your mapper that sets name, `setProtocol(OIDCLoginProtocol.LOGIN_PROTOCOL)`, `setProtocolMapper(PROVIDER_ID)` and a config map with the four `INCLUDE_IN_*` keys, then register it in that static block. `getBuiltinMappers()` (declared on `LoginProtocolFactory`) is what the admin surface reads; find its callers to be sure whether `builtins` alone is enough or the entry must also be in `defaultBuiltins` / attached by `createDefaultClientScopes`. The admin console is SPI-driven — I saw no evidence of a static frontend list, but confirm before assuming.
