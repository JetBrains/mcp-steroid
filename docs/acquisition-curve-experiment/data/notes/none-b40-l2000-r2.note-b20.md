**Hand-off note: enforce "no refresh token from client credentials" under the `strict` security profile**

**Where things live**
- Security profiles: `services/src/main/resources/{none,lax,strict}-security-profile.json`. Each is a `SecurityProfileConfiguration` (`core/.../representations/idm/`): `name`, `client-profiles`, `client-policies`. All three point at `keycloak-default-client-profiles.json`; `strict` → `keycloak-strict-client-policies.json`, `lax` → `keycloak-lax-client-policies.json`, `none` → `null` policies. `DefaultSecurityProfileProviderFactory` (`services/.../securityprofile/`) loads `<name>.json` from classpath or `conf`, defaulting to `none-security-profile`, and validates profiles/policies via `ClientPoliciesUtil`.
- Client-policy executors: `services/src/main/java/org/keycloak/services/clientpolicy/executor/` (e.g. `ConsentRequiredExecutor`, `FullScopeDisabledExecutor`, `SecureRequestObjectExecutor`). In JSON, executors are referenced by short id with a `configuration` block; several use `"auto-configure": true` (see `confidential-client`, `full-scope-disabled` in `keycloak-default-client-profiles.json`). Imitate one of these plus its factory; failures are reported as `ClientPolicyException` (`server-spi/.../clientpolicy/`).
- The flag: `OIDCConfigAttributes.USE_REFRESH_TOKEN_FOR_CLIENT_CREDENTIALS_GRANT` = `client_credentials.use_refresh_token` (`server-spi-private`), read/written through `OIDCAdvancedConfigWrapper` (`services/.../protocol/oidc/`), which already defaults it to `"false"` and can be built from either a `ClientModel` or a `ClientRepresentation`.

**Change shape and ordering**
1. New executor + factory under the executor package; register it the way sibling factories are registered.
2. Add it to a client profile in `keycloak-default-client-profiles.json`, and make sure `keycloak-strict-client-policies.json` selects that profile (its contents were not inspected — check before editing). Leave `lax`/`none` alone so a profile-less server is unchanged.

**Easy to miss**
- Admin REST and dynamic client registration both go through client policies, so validate the incoming `ClientRepresentation`; an update may omit the attribute entirely, so fall back to the stored client's value.
- Scope the check to confidential OIDC clients only (compare the public/bearer-only checks in `ClientCredentialsGrantType`, which also uses this flag to decide session persistence).

Older policy/registration patterns: `testsuite/.../client/policies/AbstractClientPoliciesTest.java`, `FAPI2Test`.
