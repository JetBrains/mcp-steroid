## Hand-off note: forbid refresh tokens on client credentials under the `strict` security profile

### The moving parts

**Security profiles** live in `services/src/main/resources/`: `strict-security-profile.json`, `lax-security-profile.json`, `none-security-profile.json`. Each is a tiny descriptor naming a client-profiles file and a client-policies file (`none` has `"client-policies": null`). `strict` points at `keycloak-strict-client-policies.json` and `keycloak-default-client-profiles.json`. The identical copies under `services/target/classes/` are build output — never edit them.

`keycloak-strict-client-policies.json` already contains the policy **"Openid-connect OAuth 2.1 confidential client"** (conditions: `client-type` = `openid-connect` plus `client-access-type` = `confidential`) which activates the client profile **`oauth-2-1-for-confidential-client`** defined in `keycloak-default-client-profiles.json`. That is the hook: the confidential/OIDC scoping the task asks for is already done by that policy, so the new rule belongs as an executor inside that profile. `lax` uses the same confidential policy, so anything added there affects `lax` too — decide deliberately.

**The setting itself**: `OIDCConfigAttributes.USE_REFRESH_TOKEN_FOR_CLIENT_CREDENTIALS_GRANT` (`"client_credentials.use_refresh_token"`, in `server-spi-private`), read/written via `OIDCAdvancedConfigWrapper.isUseRefreshTokenForClientCredentialsGrant()/set…` (defaults to `"false"`), consumed at runtime by `ClientCredentialsGrantType`. The wrapper has `fromClientModel` and `fromClientRepresentation` factories — you need both: the incoming representation for create/update, and the stored client for an update that omits the attribute.

### What to write and what to imitate

Add an executor + factory pair in `services/src/main/java/org/keycloak/services/clientpolicy/executor/` (every executor there has a sibling `…ExecutorFactory`; `FullScopeDisabledExecutor*` and `SecureLogoutExecutor*` are good shapes), register the factory the way its neighbours are, then list it in the `oauth-2-1-for-confidential-client` profile. Several default executors take `"auto-configure": true` — that is the existing idiom for "silently force the safe value on create", which matches the requirement that an unmentioned attribute ends up off; a plain check should reject with `ClientPolicyException`.

Client-policy enforcement already covers both entry points (admin REST and dynamic registration goes through `AbstractClientRegistrationProvider` / `ClientRegistrationAuth`), so no endpoint code should need touching. Make sure you handle the register **and** update client-policy events (`ClientPolicyEvent`, contexts in `org.keycloak.services.clientpolicy.context`).

### Easy to miss
- Not mentioning the attribute on update must still fail if the stored client has it on.
- `none` profile must be unaffected: keep the change confined to the profile/policy JSON and the new executor.
