**Hand-off note — enforce “no refresh token from client credentials grant” under the `strict` security profile**

**Architecture.** Security profiles are a thin layer on top of client policies. `services/src/main/resources/strict-security-profile.json` names `client-profiles: keycloak-default-client-profiles` and `client-policies: keycloak-strict-client-policies`; `none-security-profile.json` has `client-policies: null`, so a server without a profile stays unaffected if you only touch profile/policy JSON. `keycloak-strict-client-policies.json` already contains a policy “Openid-connect OAuth 2.1 confidential client” (conditions `client-type: openid-connect` + `client-access-type: confidential`) bound to the global profile `oauth-2-1-for-confidential-client` in `keycloak-default-client-profiles.json` — add the new executor to that profile’s executor list; no new policy/condition is needed. Loading/validation happens in `services/.../securityprofile/DefaultSecurityProfileProviderFactory` (reads `<name>.json` from classpath/`conf`, validates profiles+policies via `ClientPoliciesUtil`) behind the `SecurityProfileProvider` SPI (`server-spi-private/.../securityprofile`).

**Imitate.** `services/src/main/java/org/keycloak/services/clientpolicy/executor/RejectResourceOwnerPasswordCredentialsGrantExecutor{,Factory}.java`: executor handles `ClientPolicyEvent.REGISTER`/`UPDATE`, casts to `ClientCRUDContext`, calls `autoConfigure(...)` then `validate(...)`, throws `ClientPolicyException(OAuthErrorException.INVALID_CLIENT_METADATA, ...)`, with an `auto-configure` `@JsonProperty` Configuration class. Register the new factory in `services/src/main/resources/META-INF/services/org.keycloak.services.clientpolicy.executor.ClientPolicyExecutorProviderFactory`.

**Flag.** `OIDCConfigAttributes.USE_REFRESH_TOKEN_FOR_CLIENT_CREDENTIALS_GRANT` (`client_credentials.use_refresh_token`), accessed via `OIDCAdvancedConfigWrapper.is/setUseRefreshTokenForClientCredentialsGrant` (defaults false).

**Easy to miss.**
- Update-without-the-attribute must still fail if the target client has it on: use `ClientCRUDContext.getTargetClient()` alongside `getProposedClientRepresentation()`. `ConsentRequiredExecutor.beforeUpdate` is the structural model, but its logic *allows* the unmentioned case — invert it here.
- `ClientRepresentation.getAttributes()` can be null (see `SecureClientUrisExecutor`’s `Optional.ofNullable(...)`).
- Admin REST and dynamic registration both flow through `ClientCRUDContext` subclasses (`AdminClient*`, `DynamicClient*`), so one executor covers both.
- Executor ids also appear in `js/apps/admin-ui/src/context/server-info/__tests__/mock.json` and docs (`server_admin/topics/clients/client-policies.adoc`).
