**Hand-off note: reject refresh token from client-credentials grant under the `strict` security profile**

**Where the feature lives**
- Security profiles: `services/src/main/resources/{strict,lax,none}-security-profile.json`. `strict-security-profile.json` is tiny — it names a client-profiles set (`keycloak-default-client-profiles`) and a client-policies set (`keycloak-strict-client-policies`), both resolved to `services/src/main/resources/keycloak-default-client-profiles.json` and `keycloak-strict-client-policies.json`. The default-profiles file is a list of named profiles, each an array of `{"executor": "...", "configuration": {...}}` entries (e.g. `reject-implicit-grant`, `confidential-client`, `pkce-enforcer`). I did not read the strict-policies file; check which profile(s) it binds before deciding where to add your executor.
- Executors: `services/src/main/java/org/keycloak/services/clientpolicy/executor/`, each an `Xxx Executor` + `XxxExecutorFactory` pair, registered in `services/src/main/resources/META-INF/services/org.keycloak.services.clientpolicy.executor.ClientPolicyExecutorProviderFactory`.

**What to imitate**
- `RejectResourceOwnerPasswordCredentialsGrantExecutor(+Factory)` is the closest template: `Configuration` with `@JsonProperty("auto-configure")`, `executeOnEvent` switching on `REGISTER`/`UPDATE` → `autoConfigure(rep)` then `validate(rep)`, throwing `ClientPolicyException(OAuthErrorException.INVALID_CLIENT_METADATA, ...)`.
- For attribute-backed flags use `OIDCAdvancedConfigWrapper` as `DPoPBindEnforcerExecutor`, `SecureLogoutExecutor`, `PKCEEnforcerExecutor`, `HolderOfKeyEnforcerExecutor` do. The relevant constant is `OIDCConfigAttributes.USE_REFRESH_TOKEN_FOR_CLIENT_CREDENTIALS_GRANT` (`client_credentials.use_refresh_token`) in `server-spi-private`.

**Easy to miss**
- Both admin REST and dynamic registration flow through the same `REGISTER`/`UPDATE` events, so one executor covers both.
- `ClientCRUDContext` (in `services/.../clientpolicy/context/`) exposes `getProposedClientRepresentation()` and `getTargetClient()`; the latter is null on REGISTER. An UPDATE that omits the attribute must be checked against the target client — the ROPC template only inspects the proposed representation.
- "Created without mentioning it ⇒ off" implies auto-configure writes the attribute false rather than leaving it absent.
- Restricting to confidential OIDC clients (public-client/protocol check) is not covered by anything I read.
